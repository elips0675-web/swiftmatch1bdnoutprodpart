Оценка проекта SwiftMatch
🎯 Общий вердикт: 8.5 / 10
Зрелый, хорошо спроектированный продукт уровня pre-production. Видна серьёзная инженерная культура: 59 итераций, 388 тестов, идемпотентные миграции, circuit breaker, runbook'и, план отката. Это не MVP-прототип, а продукт, готовый к бете с оговорками.
✅ Сильные стороны
1. Архитектура и безопасность (9/10)
JWT в httpOnly cookie + refresh rotation с reuse detection (отзыв всей семьи при replay) — это уровень enterprise
Account lockout 5→15 мин, rate limiters (30r/s API, 5r/s auth) + nginx-уровень
Circuit breaker (opossum) для Stripe/OpenAI — защита от каскадных отказов
Idempotency-Key middleware + дедуп webhook'ов по event_id
GDPR-compliance из коробки: data export, erase, consent_log
Soft delete + audit_log на 11 таблицах — полная трассируемость
2. Тестовое покрытие (9/10)
388 тестов (307 сервер + 81 фронт) — 0 failures
E2E Playwright — 55 тестов, включая security-blind-spots (GDPR cascade, refresh race)
Кросс-браузерность (firefox/webkit)
Schema-validate в CI — дрейф схемы ломает деплой ДО миграций
3. Observability и DevOps (8.5/10)
Prometheus + Grafana (7 панелей), Sentry с фильтрацией PII
Winston JSON-логи с Request ID
k6 load-test (ramp 10→100 VU)
Docker multi-stage + healthcheck + nginx rate limiting
RTO-замер: restore из бэкапа 3.6 сек (dev), ~10-15 мин на 1GB prod
4. Документация (9.5/10)
runbook-keys.md — порядок ротации каждого ключа с проверкой
rollback-plan.md — категории инцидентов + действия
environment-setup.md — пошаговый план staging→prod
AGENTS.md с граблями (#27-53) — бесценно для преемственности
Чек-листы «готов к проду», «что осталось»
5. Продуктовый функционал (9/10)
Полный цикл знакомств + монетизация + социалка:
Geoпоиск (MySQL Spatial ST_Distance_Sphere)
Smart Matching, Attachment-тест, AI Icebreakers
Stripe + RevenueCat IAP + партнёрская экосистема (Wave 1-3)
Hangouts 2.0 с mutual like → auto-chat
B2B-маркетплейс, анти-кот верификация, псевдонимы
⚠️ Пробелы и риски
🔴 Критичные
mysql_schema.sql деградировал (этап 77)
В файле 62 таблицы, в живой БД 73
Риск: пересоздание prod-БД из schema.sql = нерабочие роуты hangouts/partners/experiments
Решение: регенерировать через mysqldump --no-data и закоммитить
Rate-limit in-memory (N+2)
express-rate-limit + lockout.js НЕ шарятся между процессами
Запрещено: pm2 cluster, Docker replicas > 1
Решение: до масштабирования — перевести на rate-limit-redis

🎯 Рекомендации (приоритеты)
Неделя 1 — критично перед продом
Регенерировать mysql_schema.sql из живой БД — убрать риск неполной схемы
Прогнать docker-compose end-to-end на staging — найти скрытые проблемы
Ввести Stripe live + SMTP + Sentry — проверить полный платёжный флоу
Перевести rate-limit на Redis — снять ограничение single-instance
Неделя 2 — мобильный релиз
Android: keystore + App Links + публикация в internal track
RevenueCat IAP: sandbox-покупка → prod-покупка
FCM: реальные push на устройство
Месяц 1 — масштабирование
S3 + CDN для фото
Log aggregation (Loki)
Нагрузочное тестирование на staging (100 VU)
Design System / Storybook — для скорости разработки
💡 Итог
SwiftMatch — это не «ещё один пет-проект», а инженерно зрелый продукт. Уровень документации, тестового покрытия и продуманности отказоустойчивости (circuit breaker, идемпотентность, reuse detection, audit log) соответствует коммерческим SaaS-продуктам.
Главный риск сейчас — не код, а инфраструктура: неполная mysql_schema.sql, не прогнанный docker-compose, не введённые ключи. Это решается за 1-2 недели системной работы, а не переписыванием.
Рекомендация: перед релизом закрыть три красных пункта (schema.sql, docker-compose e2e, Redis rate-limit) — и можно смело идти в бету.
