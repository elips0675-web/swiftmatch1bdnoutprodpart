Оценка: что доработать в SwiftMatch
По предоставленному срезу проект выглядит зрелым по тестам (2875/2875, 22 E2E-спека, большое число блокирующих гейтов), но основные доработки сейчас лежат не в «написать ещё фичу», а в трёх плоскостях:

Блокеры, которые кодом не решаются — без них «зелёное» не равно «проверено в бою».

Несколько реальных кодовых хвостов — аудит-лог, пагинация, серверное покрытие, prod-зависимости.

Доковый дрейф, который гейты не ловят: часть правил противоречит фактической реализации, а инвентарь тестов внутренне противоречив. Это опаснее, чем отсутствие правила, потому что протухшая копия читается как истина.

Ниже — приоритизированный список. Важная оговорка: я анализировал только предоставленные документы, код не открывал. Там, где ниже сказано «противоречие», это означает «документы расходятся между собой», а не «я проверил код и там баг». По канону проекта такие пункты требуют сверки с file:line.

P0 — блокеры и «зелёное, но недоказанное»
1. Реальные ключи и staging
Из Что доделать.txt (блок «Ждёт действий пользователя»):

server/.env отсутствует; check-keys.ps1 выходит 1.

Нет GitHub secrets DEPLOY_HOST, DEPLOY_USER, DEPLOY_SSH_KEY.

Нет staging-окружения для прогона E2E с реальными ключами.

Без ключей Stripe/RevenueCat-вебхуки осознанно отвечают 502/503, остальное деградирует в mock/fallback молча.

Это блокер №1: пока его нет, нельзя утверждать, что платежи, почта, пуши и S3 работают в проде, а не в демо-режиме.

2. Ротация VAPID-ключа (L1)
Приватный ключ был опубликован в README.md (коммит e8b26bf) и уже в истории GitHub. По принятому решению — только регенерация на VPS, история не переписывается. Пока ключ не заменён, он считается скомпрометированным.

3. Подтвердить зелёный CI на main после фиксов 12.10.2026
В бэклоге прямо написано: четыре джобы (server-test, test-counters, e2e, Trivy) были разобраны и исправлены, но ждёт подтверждения прогоном. Пока нет зелёного прогона на main, статус CI — не факт, а намерение.

4. Полный живой E2E на HEAD после этапов 70–77
ИНВЕНТАРЬ-ТЕСТОВ.md говорит: последний полный живой прогон — 12.10.2026 (152 в 19 спеках), а Что доделать.txt — что TEST-01 закрыт 18.10.2026 (206 passed). Это противоречие (см. P2). Кроме того, стенд 3002/8081 отдаёт код до 1fce1f1 — возвраты charge.refunded не активны, пока API не перезапустят через запуск-всего.bat. Нужен один контрольный полный прогон на актуальном HEAD с перезапущенным API.

5. Android-релиз
Домен вместо LAN-IP, keystore-подпись, App Links (assetlinks.json), AAB + Google Play, Privacy Policy/Terms, контент 17+, скриншоты. Это внешняя цепочка, но она полностью блокирует релиз.

P1 — реальные кодовые хвосты
1. audit_log не пишется на фото и GDPR-удаление
ИНВЕНТАРЬ-ТЕСТОВ.md, раздел «Известные пробелы»: INSERT/DELETE user_photos и смена moderation_status (upload.js:142,243, admin-moderation.js:78,106), а также GDPR-удаление (gdpr.js:101) не пишут следа в audit_log. При этом UPDATE профиля уже аудируется (audit.js:31). Для проекта с GDPR-контуром это заметная дыра: удаление и модерация фото — ровно те действия, которые чаще всего спрашивают на аудите.

Что сделать: добавить auditLog/auditUpdate в эти точки, покрыть тестами по образцу active-user.test.js / audit-action-enum.test.js, проверить ENUM audit_log.action (там уже был инцидент с delete_bulk, питфолл 98).

2. Пагинация у matches и notifications
GET /api/matches (social.js:334-343) — без LIMIT/OFFSET; GET /api/notifications (notifications.js:103) — жёсткий LIMIT 30 без offset/курсора. Это не «500», но:

матчи растут, и ответ будет расти линейно;

уведомления старше 30-го сообщения недостижимы в принципе.

Для сравнения: история чата уже сделана курсором по m.id с { messages, has_more, next_before } (этап 34). Логично привести матчи и уведомления к тому же контракту.

3. Серверное покрытие — слабое звено
По AGENTS.md: сервер 62.4 / 60.4 / 64.2 / 64.2 % → пороги 60 / 58 / 62 / 62. Фронт уже 71.83 / 79.35 / 68.16 / 71.83 % → 69 / 77 / 66 / 69. То есть серверная половина заметно ниже, а именно там живут SQL, вебхуки, auth и платежи. Следующий разумный этап COV — не фронт, а сервер: routes/*, jobs/*, ws.js, middleware.js. Пороги поднимать только вверх, по правилу «факт − 2 п.п.».

4. 28 moderate в prod-зависимостях server/
Что доделать.txt: @sentry/node 9 → 11 (цепочка @opentelemetry/*), firebase-admin → 14.5.0, bull → advisory в uuid (предлагаемый npm «фикс» — понижение до bull@1.1.3, что бессмысленно). 0 high / 0 critical, достижимость низкая, поэтому не срочно, но это единственный известный класс, который со временем может стать high. Нужен план обновления, а не «подождём».

5. Живые внешние интеграции проверены только моками
Для анализа.txt: RevenueCat / FCM / Twilio / OpenAI / Rekognition — только мок/fallback. SMTP и S3 закрыты контрактными смоуками (maildev — Stage 65-66, zenko/cloudserver — Stage 67), это хорошо. Но:

SMTP-флоу «поднимается → письмо доходит» против реального сервера не покрыт;

Bull/Redis-ветки очередей не гоняются живьём (queue-monitor.test.js — фейковый источник очередей);

FCM/Twilio/OpenAI/Rekognition — только мок.

Минимум: контрактные смоуки против эмуляторов для FCM/Twilio (по образцу maildev), для OpenAI/Rekognition — записать контракт ответа и проверять его на моке.

6. Swagger / недокументированные роуты — проверить актуальность
ИНВЕНТАРЬ-ТЕСТОВ.md говорит: «Swagger покрывает 47 операций (44 пути) при 212 вызовах, пересчитано 04.10», и что «нет теста на недокументированные роуты». Но в AGENTS-pitfalls.md (питфолл 101) сказано, что живой гейт печатает 234 операции / 198 путей / 242 роута, а swagger-coverage-audit.mjs и джоба swagger-coverage в CI есть. Похоже, пункт инвентаря устарел. Прежде чем брать в работу — прогнать npm run check:swagger-coverage и либо снять пункт, либо обновить формулировку.

P2 — доковый дрейф (важно, потому что «правило = код»)
Это самый недооценённый блок. Гейт check:docs ловит раскладку, запрещённые формулировки и версии стека, но не ловит смысловые противоречия между правилами. А в проекте, где «правила — единственный источник истины», протухшее правило опаснее бага: агент читает его как руководство к действию.

1. AGENTS-security.md противоречит фактической auth-модели
В AGENTS-security.md: «JWT: 256-bit ключ, 7d expiry, Bearer header» и «основной Bearer-токен хранится в sessionStorage… переход на httpOnly cookie отложен (этап 28, ADR)».

В project-context.md и Для анализа.txt: этап 33 — JWT в httpOnly cookie sm_token (24h) + sm_refresh (7d), мидлвари читают Bearer ?? cookie, web-фронт не хранит токен в JS-storage.

В AGENTS-workflow.md (шаблон промта) уже правильно: «httpOnly cookie через setAuthCookies… Не менять на localStorage».

То есть внутри одного набора правил два разных ответа на вопрос «где живёт токен». Это надо привести к одному виду: AGENTS-security.md обновить под cookie-модель, оставив Bearer только для нативных сборок.

2. AGENTS-security.md противоречит rate-limit
Там: «auth 1000/мин, /api/ 600/мин, лайки 30/мин».

В README.md / Для анализа.txt: «auth 60/мин (поднят для E2E)», глобальный 600/мин, nginx auth 10r/s.

Если разработчик будет реализовывать новый лимитер «по правилу», он поставит 1000/мин и получит расхождение с периметром. Нужно сверить с middleware/limiters.js и зафиксировать одно значение.

3. Лимит загрузки: 5 MB или 10 MB?
README.md: «MIME-фильтр… лимит 10MB».

AGENTS-security.md и AGENTS-production.md §7: «ограничение 5MB».

Сверить с upload.js и оставить одно значение.

4. ИНВЕНТАРЬ-ТЕСТОВ.md внутренне противоречив
Файл в одном документе содержит:

заголовок «Фронт — 95 файлов, 881 теста» (совпадает с test-inventory.json);

примечание «сверх 76 продуктовых файлов (516 тестов)… ещё 26 файлов гейтов (621 тест), всего 102 файла = 1137 тестов» — это устаревший срез;

раздел «Скрипты гейтов — 27 файлов, 670 тестов» (совпадает с машиной);

строку «Гейты, у которых есть собственные тесты (169 в 6 файлах)» — устарело, файлов гейтов 27.

То есть машина говорит 122/1551, а проза в середине — 102/1137. Гейт test-counter-audit сверяет только конкретные строки, а не весь документ, поэтому это проезжает.

5. «Последний живой E2E» — 12.10 или 18.10?
ИНВЕНТАРЬ-ТЕСТОВ.md: «последний полный живой прогон — 12.10.2026 (152 в 19 спеках)». Что доделать.txt: «TEST-01 закрыт 18.10.2026 (Stage 64) — 206 passed». Одно из двух устарело. Судя по Для анализа.txt («живой полный прогон 18.10.2026 — 206 passed»), устарел инвентарь.

6. Секция «Известные пробелы покрытия» устарела по закрытым пунктам
Там до сих пор:

«N4 — нет гейта CHECK/ENUM/UNSIGNED, кандидат check-enum-constraints.mjs» — гейт есть, джоба enum-constraints в CI есть.

«N5 — N+1-аудит написан, но в CI не подключён» — джоба n-plus-one в CI есть.

«Swagger 47/212» — вероятно, устарело (см. P1.6).

Эту секцию надо перечитать целиком и снять закрытое, иначе она читается как «открытые дыры», которых уже нет.

7. Число миграций: 57, 60 или 71?
README.md и project-context.md: «57 пронумерованных .sql».

Для анализа.txt: «60 нумерованных миграций».

Что доделать.txt: упоминает database/migrations/071_quiet_hours.sql.

Значит, фактически ≥71. Число миграций не покрыто ни test-counter-audit, ни check:docs. Либо убрать число из прозы, либо завести гейт (простая проверка «число файлов в migrations/ совпадает с числом в README/project-context»).

8. AGENTS-workflow.md: «обновить context.txt»
В разделе «Этап 4 — Верификация» написано «Обновить документацию (context.txt, AGENTS.md…)». Но context.txt — исторический архив (шапка «ИСТОРИЧЕСКИЙ СРЕЗ 26.09.2026»), его не обновляют. Формулировку надо поправить, иначе агент будет писать в архив.

9. «23 джобы ci.yml + 7 deploy.yml»
Для анализа.txt фиксирует это на 12.10.2026, но в README.md таблица ci.yml содержит заметно больше джоб (lint, lint-server, typecheck-gate, e2e, e2e-gate, test, test-server, schema-drift, order-by, secrets-leak, test-counters, deploy-persistence, deploy-rollout, dependency-integrity, dependency-audit, docs-canon, n-plus-one, mysql-race, queue-smoke, backup-smoke, enum-constraints, env-consistency, env-parity, swagger-coverage, prod-mock, security-headers, alerts, mirrors, blocks-coverage, query-param, migrations-lag — это уже >30). Число «23» устарело; лучше либо не писать точное число, либо гейтить его.

10. project-context.md — исторический срез в середине файла
Файл начинается как актуальный контекст, затем идёт большой блок «Срез на август 2026 (этапы 27–59) — исторический, не текущее состояние» с 388/388 и 54 таблицами. Он помечен, это хорошо, но читатель, открывший файл с середины, может принять его за текущее. Стоит либо вынести в docs/archive/, либо усилить шапку блока (как у context.txt).

Рекомендация по P2: добавить в check:docs 3–4 проверки на согласованность:

auth-модель: в AGENTS-security.md не должно быть «Bearer в sessionStorage» как текущего состояния, если project-context.md говорит cookie;

rate-limit: числа auth/api в AGENTS-security.md совпадают с README.md/middleware/limiters.js;

лимит загрузки: одно значение в README/AGENTS-security/AGENTS-production;

число миграций: README.md/project-context.md совпадает с ls database/migrations/*.sql.

Это дешевле, чем каждый раз ловить дрейф глазами.

P3 — nice-to-have, не горит
Storybook / Design System — «не начато», низкий приоритет, пока UI-регрессии не стали болью.

IAP sandbox-тест покупок — заблокирован внешне (после публикации в Google Play).

Cross-browser — осознанное ограничение (CROSS_BROWSER=1), по умолчанию только chromium.

CSRF csrfGuard — осознанно отложен до выноса API на отдельный домен; триггер зафиксирован. Не «забыто», но при выносе API включать обязательно.

Дальнейшее покрытие ядра — фронт уже хорош; остаток в chats.tsx — функции внутри замоканных компонентов, недостижимые в jsdom, а не пропущенные.

Предлагаемый порядок этапов
Этап A (доковый аудит, 1 день). Привести AGENTS-security.md к cookie-модели и фактическим лимитам; сверить 5/10 MB; почистить ИНВЕНТАРЬ-ТЕСТОВ.md (убрать устаревшее примечание 76/516/26/621, обновить «169 в 6 файлах», снять закрытые N4/N5/Swagger, поправить «последний живой E2E»); убрать/гейтить число миграций; поправить AGENTS-workflow.md про context.txt. Прогнать check:docs, check:mirrors, test-counter-audit --fix. Добавить 3–4 проверки согласованности в check:docs.

Этап B (кодовые хвосты, 2–3 дня). audit_log на user_photos + GDPR-удаление (upload.js, admin-moderation.js, gdpr.js) с тестами. Пагинация matches и notifications по образцу истории чата ({ items, has_more, next_before }) с тестами. Проверить и либо снять, либо обновить пункт про Swagger.

Этап C (серверное покрытие + deps, 2–3 дня). Поднять серверное покрытие с 62/60/64/64 к ~65–68 % по ключевым модулям (routes/*, jobs/*, ws.js, middleware.js), поднять пороги по правилу «факт − 2». План обновления @sentry/node 9→11, firebase-admin → 14.5.0, разобраться с bull/uuid (не понижением до 1.1.3).

Этап D (живое доказательство, зависит от владельца). Ключи + staging + GitHub secrets + VAPID-ротация + полный живой E2E на HEAD с перезапущенным API + Android release chain. Без этого этапа всё предыдущее — «зелено в теплице».

Итог
Проект в хорошей форме: тестовая база большая, гейты продуманы, питфоллы задокументированы. Главные риски сейчас — не количество кода, а расхождение правил с реальностью и отсутствие живого прогона с реальными ключами. Если выбирать один самый полезный следующий шаг — это этап A (доковый аудит + 3–4 новые проверки в check:docs), потому что он дёшев, ловит класс проблем, который уже дважды приводил к неверным выводам (питфоллы 52, 101), и разблокирует доверие к остальным документам. Сразу за ним — B (audit_log + пагинация), потому что это реальные пользовательские и комплаенс-дыры, а не косметика.
