💪 Сильные стороны (Что сделано блестяще)

Беспрецедентный уровень CI/CD гейтов
Внедрение кастомных скриптов (secrets-leak-audit, deploy-persistence-audit, schema-drift-audit, test-counter-audit) — это уровень зрелости, который редко встречается даже в средних компаниях. Проект защищает сам себя от дрейфа конфигураций, утечек секретов и устаревания цифр в документации. В `ci.yml` 8 джоб, в `deploy.yml` 7.

Глубокая проработка безопасности (Security by Design)
Закрыты реальные дыры: IDOR в профилях/фото, XSS-санитизация на сервере, гонки при взаимных лайках (race conditions), ротация refresh-токенов с отзывом "семьи" (`server/src/routes/auth.js`, `family_id` + reuse-детект по `affectedRows = 0`).
Админка защищена TOTP 2FA (`server/src/index.js:178-188`, только при `totp_enabled = 1`) и блокирующим adminAuth middleware (401 без токена, 403 не-админу).
Graceful degradation: система корректно деградирует (in-memory fallback, mock-платежи), если внешние сервисы (Redis, SMTP, OpenAI) недоступны или не имеют ключей.

Феноменальная тестовая база

Проверка: `node scripts/test-counter-audit.mjs` → «Итог: счётчики в документации совпадают с прогоном».)
Тесты проверяют не только "зеленый" путь, но и регрессии (мутационное тестирование логики гейтов: `scripts/secrets-leak-audit.test.mjs`, `scripts/test-counter-audit.test.mjs`, `server/src/__tests__/schema-drift.test.js`, `server/src/__tests__/deploy-persistence-audit.test.js`), гонки потоков (`race.test.js`, `race.mysql.test.js`) и edge cases — например, откат транзакций при реплее вебхуков (`premium-webhook.test.js:107,125`).

Живая и самоочищающаяся документация
AGENTS.md — эталонный системный промпт для AI-ассистентов, содержащий 51 конкретную "граблю" (pitfalls) с примерами.

⚠️ Зоны риска и технические долги (Что требует внимания)

Отсутствие реальных API-ключей (Блокер для прода)
Проект работает в режиме mock/fallback. Для полноценного запуска необходимо внести реальные ключи: Stripe, SMTP, Sentry, S3, Redis, FCM, RevenueCat, Twilio, AWS Rekognition, OpenAI. Без этого функции модерации, пушей и реальных платежей не активируются.
ВАЖНАЯ ПОПРАВКА К РЕКОМЕНДАЦИЯМ НИЖЕ: на VPS ключи надо класть в КОРНЕВОЙ `.env`, а не в `server/.env` — `docker-compose.yml:83-84` читает `env_file: - .env`, и перечисление всех этих ключей есть только в `server/.env.example` (закомментировано), в корневом `.env.example` их нет вообще. Это уже заведено в бэклог (P2, `.env` + `rsync --delete`).

Умеренные (Moderate) уязвимости в зависимостях
В `server/` — 25 moderate advisory, в корне — 2 (`react-router-dom`). Проверка: `npm audit --omit=dev` в обоих каталогах; гейт `npm run audit:prod` (корень + `server/`) падает только на high/critical, поэтому moderate — не блокер.
(БЫЛО «например, в @sentry/node, firebase-admin, bull» — неточно: в отчёте всего два advisory-корня, `firebase-admin` там ОТСУТСТВУЕТ. Реально: `@opentelemetry/core <2.8.0` (тянет `@sentry/node@^9.14.0`) и `uuid <11.1.1` (тянет `bull@^4.16.5`). `npm audit fix --force` предлагает `@sentry/node@11.1.0` (ломающее обновление, нужно) и `bull@1.1.3` (понижение мажора — артефакт npm, брать нельзя).)

Незакрытые P0, которых не было в исходной оценке
• **P0-E — модерация фото не fail-closed.** `user_photos.moderation_status` по умолчанию `'approved'` (`database/mysql_schema.sql:1246`, `database/migrations/001_add_moderation_columns.sql:5`), INSERT в `upload.js` статус не пишет, а `GET /api/photos/:userId` (`upload.js:224`) вообще не фильтрует по статусу. То есть фото попадает в профиль сразу и остаётся там. Ждёт продуктового решения: fail-closed (`'pending'` + фильтр `moderation_status = 'approved'`) или оставить как есть.
• **P0 #5 — нет списка активных сессий и отзыва по одной.** Есть только `POST /api/auth/logout-all` (`auth.js:346`), который глушит всё сразу. Нет `GET /api/auth/sessions`, нет отзыва отдельной сессии, нет UI. Токены при этом в БД уже есть (`refresh_tokens` с `family_id`, `revoked`, `fingerprint`).
• **P0-B (WebSocket)** — был открыт до 30.09, закрыт этапом 25.

E2E не исполняются в CI
150 E2E-тестов реальны и проходили 150/150 (этап 124, Docker-фича), но в CI только перечисляются: `ci.yml:71` — «E2E считается статически (--list), БД не нужна». В бэклоге это P1 «B2».

Сложность онбординга нового человека
Хотя для AI-агента структура идеальна, новый human-разработчик может потеряться в объёме исторических логов (`context.txt` — 144 894 байта = 141.5 КиБ, `Что сделано.txt` — 1 936 строк / 318 КБ). Митигация: наличие `CONTRIBUTING.md` и скрипта `test-counter-audit` частично решает эту проблему.
(БЫЛО «Что сделано.txt содержит более 120 этапов» — НЕВЕРНО: там 66 заголовков этапов, 53 уникальных номера, максимум 87. Число ~120 — это количество УПОМИНАНИЙ «Этап N». Полная нумерация этапов до 126 живёт в `Что доделать.txt`.)

Мобильная сборка (Capacitor)

🚀 Рекомендации к действию (Next Steps)

Фаза "Staging & Keys" (Приоритет P0)
1. Развернуть проект на тестовом VPS через `docker compose up -d --build` (как описано в этапе 117 — ссылка валидна, `Что доделать.txt:854`).
2. Сгенерировать и внести реальные ключи в КОРНЕВОЙ `.env` (начать с Stripe Test Keys, SMTP и Sentry DSN для проверки базовых флоу). Ключи из `server/.env` на VPS не подхватятся — compose читает корневой.
3. Перегенерировать VAPID-ключи (старый приватный ключ попал в историю Git — этап 24). Переписывать историю не нужно, достаточно регенерации на проде.
4. ДОБАВЛЕНО ПОСЛЕ ПРОВЕРКИ: закрыть P0-E (очередь модерации фото) и P0 #5 (список активных сессий + отзыв по одной). Без них пункт «Готовность к проду» не растёт.

Нагрузочное тестирование на Staging (Приоритет P1)
Запустить `k6/load-test.js` на 100 VU на реальном staging-сервере (а не localhost), чтобы подтвердить, что глобальный rate-limiter (600 req/min, `server/src/middleware/limiters.js:36`) и пул MySQL (20 соединений, `server/src/db.js:10`) держат нагрузку без деградации.

Плановое обновление зависимостей (Приоритет P2)
Выделить отдельный спринт на мажорное обновление `react-router-dom` (v6.30.4 → v7.18.4) и `@sentry/node` (v9.14.0 → v11.1.0) для закрытия оставшихся moderate advisory, предварительно прогнав полный E2E-набор. `bull` НЕ понижать до предложенного npm «1.1.3» — обновлять вручную осознанно.

Подготовка к мобильному релизу
Настроить домен и получить SHA-256 fingerprint для `assetlinks.json` (Android App Links).
Создать проект в RevenueCat, настроить вебхуки и собрать Release APK с подписью. Первый шаг — просто собрать Debug APK: сейчас в репозитории нет ни одного `.apk`.
