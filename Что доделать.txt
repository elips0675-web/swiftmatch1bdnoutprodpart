## 🔴 P0 — продуктовые дыры

### N3, вторая половина P0-E — очередь модерации фото мертва (дипсик #5, qwen «модерация фото»; **решение владельца принято 07.10 — вариант Б**)

Цепочка разорвана в трёх местах, каждое проверено:

- `database/mysql_schema.sql:1249` — `moderation_status varchar(20) DEFAULT 'approved'`;
- `server/src/routes/upload.js:123` — `INSERT INTO user_photos (user_id, url, sort_order)`, статус не задаётся → **каждое загруженное фото попадает в `approved`**;
- `server/src/routes/admin-moderation.js:31` — очередь фильтрует `WHERE p.moderation_status = 'pending'`, то есть всегда пуста;
- `admin-moderation.js:45` — approve: `UPDATE ... WHERE id = ? AND moderation_status = 'pending'`, **`affectedRows` не проверяется**, поэтому 200 возвращается даже при нуле обновлённых строк.

Тест `server/src/__tests__/admin-moderation.test.js:98-104` подтверждает ровно этот вакуум: `pool.query.mockResolvedValueOnce([[], []])`, проверяется только `expect(res.status).toBe(200)`.

**Решение владельца (07.10.2026) — вариант Б:** `PHOTO_MODERATION_MODE` в `runtime.js`, INSERT всегда пишет `'pending'`, режимы `strict|permissive` выбирают, кто публикует; **существующие фото остаются `approved`** (без миграции). При `ALLOW_UNMODERATED_PHOTOS` (вне прода, ключей AI нет) INSERT обязан сразу писать `'approved'` в permissive-режиме, иначе в dev фото станет невидимым.

Открыто (этап 41 закрыл только «отказ в проде без модератора»): `'pending'` не пишет ни одна строка кода (`grep "'pending'"` по `server/src` находит только `WHERE moderation_status = 'pending'` в `admin-moderation.js:31` и чужие таблицы), поэтому `GET /api/admin/moderation/photos/pending` пуст всегда, а approve/reject (`admin-moderation.js:45,59`) обновляют 0 строк и отвечают 200; плюс фильтр `moderation_status = 'approved'` в трёх точках выдачи (`profile.js`, `upload.js:224`, лента) и проверка `affectedRows` в approve/reject.

## 🟡 P2 — nice-to-have, дошлифовка

### N10. Если E2E-teardown упал, `e2e_*` остаются в БД (P2, остаток от 05.10.2026)

Внешняя оценка qwen2 предлагает «улучшить E2E teardown» и «обернуть прогон в транзакцию с ROLLBACK / ephemeral БД». Факт: мусор после прогона был, но причиной был не «падение teardown», а префикс `ban_rt_*`, который `global-teardown` не чистил (исправлено этапом 30). **Предложение с транзакцией отклонено как технически невыполнимое**: API и фронт — отдельные процессы, соединений много, Playwright ходит по HTTP; в CI чистоту обеспечивает одноразовый сервис `mysql:8.0` на джобу. Остаток: если teardown упадёт, `e2e_*`-юзеры останутся. Чинится либо «сделать teardown независимым от основного прогона» (`globalTeardown` отдельным шагом с `if: always()`), либо честной проверкой после прогона («в БД не осталось ни одного `e2e_*`» как шаг джобы).

### Дефект гейта счётчиков: `ROW_RE` не терпит экранированную черту и `--fix` добавляет дубль строки (P2)

`scripts/test-counter-audit.mjs:245` — `const ROW_RE = /^\| `([^`]+)` \|[^|]*\| (\d+) \|$/gm`: средняя ячейка не может содержать `|`, поэтому описание вида «команда `npm test \|\| true`» (валидный markdown) **не парсится вообще**. Дальше гейт сообщает ложное «нет строки в инвентаре», а `fixInventoryRows` не чинит существующую строку, а **дописывает вторую такую же** — то есть `--fix` портит инвентарь (в `test/ИНВЕНТАРЬ-ТЕСТОВ.md` появился дубль, пришлось удалять руками; сам гейт дубль не замечает, потому что `parseInventoryRows` складывает строки в `Map` по имени файла).

Как чинить (самостоятельная правка гейта, с тестами и ломкой): (1) `ROW_RE` — разрешить экранированную черту в средней ячейке (`[^|]*(?:\\.[^|]*)*`); (2) `fixInventoryRows` — если строка для файла уже есть, обновлять её, а не добавлять вторую; (3) тест на описание с `\|` и тест «две строки на один файл — дубликат, а не тишина». Суть гейта (счётчик тестов совпадает с прогоном) сохраняется, чинится только парсер.

### L2. Расхождение двух хостовых nginx-конфигов

В образ едет `nginx/swiftmatch.http.conf` (`Dockerfile:30`). Два других файла — конфиги **хостового** nginx на VPS, и они расходятся:

| Файл | Роль | Расхождения |
|---|---|---|
| `nginx/swiftmatch.http.conf` | образ, HTTP:80 | `limit_req` 60r/s (`/api`) и 10r/s (`/api/auth`), `client_max_body_size 20M`, `proxy_read_timeout 86400s`, `location = /healthz` |
| `nginx/swiftmatch.conf` | хост, TLS:443 | 30r/s и 5r/s, `10M`, нет WS-таймаута |
| `nginx.conf` (корень) | хост, TLS:443 | **нет `limit_req` вообще**, **нет `client_max_body_size`**, `proxy_read_timeout 60s` |

Не выбрано, какой из двух хостовых конфигов — эталон. Риск: хост с `nginx.conf` не ограничивает скорость запросов и рвёт WS на 60-й секунде. Требует решения владельца и правок в документации под выбранный файл.

### L3. Graceful shutdown обрабатывает только SIGTERM

`server/src/index.js:337-343` — обработчик ровно одного сигнала, без таймаута и без `SIGINT`. Последствия: `docker compose stop` (по умолчанию 10 с) при медленном запросе к БД может оборвать транзакцию; Ctrl+C не даёт приложению закрыть пул соединений и WS. Нужен `server.close()` с deadline и явной обработкой обоих сигналов.

### L4. Node 20 в `ci.yml` против Node 22 в проде

`deploy.yml` объявляет `NODE_VERSION: '22'`, `ci.yml` часть джоб крутит на 20. Прод-образ — `node:22-alpine`. Пока джобы совпадают, расхождение не проявляется, но любой новый advisory уровня «только в 20» проверит не тот раннер. Нужно выровнять на 22 во всех джобах `ci.yml`.

## Правила работы с журналами и бэклогом

- **Бэклог ≠ история.** Новые закрытые пункты пишутся в `Что сделано.txt` (хроника этапов); из бэклога закрытый пункт удаляется или помечается ✅. Полная история прошлых срезов — в `docs/agenda-archive.md`.
- **Числа в шапках** — только прогоном `node scripts/test-counter-audit.mjs` (exit 0), не перепечаткой: журналы и оценки проекта гейтом счётчиков не покрыты (покрыты 5 файлов, список в `scripts/test-counter-audit.mjs:237-241`).
- **Зеркала `test/Что доделать.txt` и `test/Что сделано.txt`** синхронизируются с корнем побайтово после каждой правки журналов.
- **Кодировка:** править файлы node-скриптами + `cmd /c "node ... > file 2>&1"`, затем читать файл (PowerShell ломает кириллицу).
- **Пункт без цитаты кода** (`file:line`-цитата, проверенная по коду) в бэклог не попадает.
- **Фича = флаг** (по умолчанию off, включение через админку); DoD: флаг + тест + i18n + `check-console` + актуальный инвентарь тестов.
- **Сначала фикс, потом тест:** тест, фиксирующий баг, пишется после устранения причины.
- **Пороги coverage — буфер +2 п.п.** ниже фактического.
- **Промты про БД** требуют идемпотентные миграции (без ручных ALTER вне миграций), обновление `schema.prisma`/эталона, индекс при необходимости, обратную совместимость.
