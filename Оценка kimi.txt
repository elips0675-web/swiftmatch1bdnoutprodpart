Оценка SwiftMatch — Август 2026
Итог: 7.5 / 10 — «готов к staging и закрытой бете, не готов к открытому продакшену без внешних действий».
Проект представляет собой высококачественный full-stack продукт с продвинутой архитектурой, но существует разрыв между «код готов» и «можно открыть для пользователей».
✅ Сильные стороны (что сделано на уровень enterprise)
Таблица

Тестовое покрытие	366 сервер + 86 фронт + 150 E2E = 0 failures. Это редкость даже для команд.
Архитектура фич	Полный цикл дейтинга + монетизация (Stripe + IAP) + партнёрка + ивенты + B2B — всё интегрировано в единую схему.

i18n и data-консистентность	RU/EN parity, translation keys в БД, сортировка через t().localeCompare().

🔴 Критические риски (блокеры и техдолг)
Таблица
Риск	Уровень	Почему важно
Schema drift	🔴 Высокий	mysql_schema.sql = 62 таблицы, живая БД = 73. Пересоздание БД из schema.sql даст неполную схему (29 таблиц только из миграций). CI-инит БД создаёт тестовую БД из неполной схемы — schema-validate.mjs не ловит это, т.к. сверяет «сам с собой».
Windows-центричность	🟠 Средний	Основной workflow — Laragon, PowerShell, .bat. Prod будет Linux. Не все скрипты имеют .sh-эквиваленты, пути захардкожены (C:\swiftmatch1bd...).
In-memory rate-limit	🟠 Средний	express-rate-limit и lockout.js используют память процесса. При масштабировании на 2+ инстанса (pm2 cluster / Docker replicas) лимиты перестанут работать. Есть решение (Redis store), но оно не внедрено.
Отсутствие staging-окружения	🔴 Высокий	Docker Compose «не прогонялся end-to-end» (по вашим же записям). Нет VPS, домена, SSL. Невозможно проверить реальное поведение под нагрузкой.
CSRF / fingerprinting	🟡 Низкий	SameSite=Lax + Bearer для нативки — приемлемо для текущей архитектуры, но при выносе API на поддомен понадобится double-submit token. Fingerprint сессий отложен.
Redis fallback crash (исправлен, но требует мониторинга)	🟡 Низкий	Этап 42 починил краш при недоступном Redis, но нужно убедиться, что fallback не DDOS'ит MySQL при массовом cache-miss.
⛔ Блокеры перед продакшеном (что нужно сделать вне кода)
VPS + Docker Compose end-to-end — поднять на реальном железе, проверить healthcheck'и, сеть между контейнерами, volume persistence.
Домен + SSL — Let's Encrypt + auto-renewal, проверка wss:// (WebSocket через HTTPS).
Реальные API-ключи — минимум: Stripe (test mode для staging), SMTP (Mailtrap/Resend), Sentry DSN, Redis.
k6 100 VU на staging — проверить RADAR_PRE_LEAK_64 (память MySQL под нагрузкой), убедиться что DB_POOL_MAX=20 достаточно.
Android-релиз — keystore, AAB, App Links (assetlinks.json + SHA256), Google Play Console (17+, Privacy Policy).
Мониторинг — UptimeRobot + Grafana alerts (CPU, 5xx, DB connections).
📋 Приоритеты действий
Неделя 1 (разблокировать staging):
Перегенерировать mysql_schema.sql из живой БД (mysqldump --no-data) или добавить в CI node database/migrations/migrate.js после mysql_schema.sql (этап 79 частично это сделал, но стоит перепроверить).
Поднять VPS (Ubuntu), установить Docker, склонировать репо, собрать docker compose up -d --build.
Прогнать schema-validate.mjs + migrate.js на чистой БД на VPS.
Неделя 2 (ключи и смоук):
Вписать Stripe test keys, SMTP (Mailtrap), Sentry DSN.
Прогнать E2E против staging (реальные ключи, реальный домен).
Проверить backup/restore цикл на VPS (scripts/backup-mysql.sh + verify-backup.mjs).
Неделя 3 (нагрузка и безопасность):
k6 100 VU, мониторинг free -m / Threads_connected.
Настроить UptimeRobot + Telegram/Slack алерты.
При необходимости — перевести rate-limit на Redis store (если планируется >1 инстанс API).
💬 Вердикт
Кодовая база — production-grade. Архитектура, тесты, документация (AGENTS.md, runbook-keys, rollback-plan) находятся на уровне команды из 5–10 человек.
Но: проект сейчас в состоянии «отличный код в репозитории, который никогда не работал на реальном железе с реальными ключами». Разрыв между «написано» и «работает у пользователей» закрывается не кодом, а инфраструктурными действиями (VPS, ключи, домен, сторы).
Если вам нужна одна цифра: 7.5/10 (код 9/10, инфра 6/10).
