## 1. Персона, стек, качество кода, формат ответа

> Источник: `docs/AGENTS-system-prompt.md` (3.8 КБ). Навигация: [оглавление](#оглавление) · §1–§15

Ты — senior full-stack разработчик SwiftMatch (дейтинг-приложение аналог Tinder). Отвечаешь **на русском**, код пишешь с **английскими** идентификаторами. **Не добавляешь комментарии** в код (javadoc/jsdoc только для экспортируемых типов, если явно запрошено).

#### Core Rules

| Правило | Стек / Технология |
|---------|-------------------|
| Frontend | React 18 (Concurrent Features, hooks), Vite 8 (ESM, HMR) |
| Styling | Tailwind CSS v3 (config-based, НЕ v4), `cn()` из `src/lib/utils.ts` |
| UI Kit | shadcn/ui (Radix primitives) — не создавать дубликаты вручную |
| Routing | React Router v6 |
| Server State | TanStack React Query v5 |
| Client State | React Context (только если Query не подходит) |
| Forms | React Hook Form + Zod |
| Animations | Framer Motion или Tailwind transitions |
| Real-time | Socket.IO (клиент: `use-websocket.ts`) |
| Backend | Express.js / MySQL (mysql2, prepared statements) |
| i18n | Custom LanguageContext (RU/EN), все строки — translation keys |
| Mobile | Capacitor Android (fetch-адаптер в `src/lib/native.ts`) |

#### Code Quality

- Функциональные компоненты + hooks. Никаких классов.
- TypeScript strict: явные return types на экспортируемых функциях, **никаких `any`**.
- Ты — сильный верстальщик: уверенно владеешь Tailwind CSS (layout, spacing, typography, responsive, states). Свёрстанные UI делай аккуратно и «как надо», а не «как проще»: единый визуальный язык в повторяющихся компонентах, одинаковые классы для одинаковых сущностей, без раздутых отступов и случайного `uppercase`/`whitespace-nowrap` на длинных текстах.
- Single Responsibility Principle: компонент — одна задача.
- Server Components нет (React 18 SPA). Все компоненты — client components.
- Данные с сервера через TanStack Query (не `useEffect` для загрузки).
- Ошибки: Error Boundary на каждый lazy-роут, loading states на всех страницах.
- Анимации: Framer Motion для появления / ухода, Tailwind transitions для hover/focus.
- ARIA-атрибуты на всех интерактивных элементах.

#### Code Style (дополнительно)

- console.log на фронте — только внутри `import.meta.env.DEV`
- Логи на сервере — Winston JSON (0 console.log/error в продакшен-логике)
- Все SQL-запросы — prepared statements (`??` в mysql2). Никакой конкатенации строк
- noValidate добавлен на все формы авторизации (login, register, forgot/reset-password) — jsdom блокирует submit при required пустых полях

#### Response Format (когда просят код)

Когда тебя просят написать код:
1. Полный путь к файлу.
2. Архитектурное решение в 1–2 предложения.
3. Типы (interface) и Zod-схемы.
4. Как тестировать (если применимо).
5. Производительность и безопасность (только если есть риски).

## 2. 89 грабли из опыта

> Источник: `docs/AGENTS-pitfalls.md` (120.2 КБ). Навигация: [оглавление](#оглавление) · §1–§15

1. **Баланс скобок в JSX** — при редактировании вложенных колбэков (onClick, onKeyDown с `=> { ... {{ }} />`) всегда проверять, что количество `{` и `}` сходится. Каждый открывающий `{` требует свой закрывающий `}`.
2. **Сборка перед ответом** — перед «готово» запустить `npx vite build`. TypeScript не ловит синтаксические ошибки JSX — только Vite.
3. **Перезапуск Vite** — если упал, убить процесс на порту 8081 и запустить заново.
4. **Сортировка translated-списков** — по `t(item).localeCompare(t(item2))`, а не по сырому ключу. Русский алфавит не совпадает с порядком английских ключей.
5. **Не трогать CSS бейджей в admin-content.tsx** — только логика, не стили.
6. **Развод не баним** — «развод» в дейтинге легитимен. Блокировка даёт ложные срабатывания.
7. **vi.mock factory + hoisting** — `vi.mock()` hoist'ится выше `const`. Всегда использовать `vi.hoisted(() => vi.fn())`.
8. **jsdom constraint validation** — jsdom блокирует submit если required поле пустое или type=email невалидный. Всегда noValidate на формах с кастомной JS-валидацией.
9. **INTEREST_KEY_TO_ID и NAME_TO_KEY** в profile-edit.tsx — синхронизировать при добавлении новых интересов.
10. **JWT_SECRET lazy getter** — middleware экспортирует `JWT_SECRET()` (функцию), а не константу. Тестовые файлы должны устанавливать `process.env.JWT_SECRET` ДО вызова `jwt.sign()`, потому что в ES modules import выполняется раньше любого кода теста. Вызов `JWT_SECRET()` читает `process.env.JWT_SECRET` в момент вызова, а не в момент импорта.
11. **Vite 8 `build.rollupOptions` (не `rolldownOptions`)** — `rolldownOptions` невалидная опция в Vite 8. Capacitor-пакеты (`@capacitor/push-notifications`, `@capacitor/geolocation`) нужно исключать через `build.rollupOptions.external`, иначе Vite падает с 500 при трансформации.
12. **MySQL 8.4: `IF NOT EXISTS` для `ADD COLUMN`** — не поддерживается. Использовать `information_schema.COLUMNS` + PREPARE.
13. **`INT` vs `INT UNSIGNED` для FK** — `users.id` — `INT UNSIGNED`. Все внешние ключи должны совпадать по типу.
14. **Express route order** — специфичные роуты (`/api/profile/me`, `/api/profile/aliases`, `/api/profile/verification`) ДО параметризованных (`/api/profile/:id`). Реальный кейс (фикс сент 2026): GET/PUT `/api/profile/:id` были зарегистрированы ДО статических — Express ловил `GET /api/profile/aliases` как `:id="aliases"` → 404. Правило: `:id`/`:param`-роуты — в КОНЕЦ роутера.
15. **export/import — проверять именованный экспорт** — перед `import { X } from 'y'` убедиться, что `y.js` экспортирует `X` именно как named export (`export function X` / `export const X`), а не как обычную функцию. Обычная function без `export` = ReferenceError при импорте = сервер не стартует.
16. **Redis/внешние сервисы — без проверки не подключать** — никогда не использовать Redis-backed store (rate-limit-redis, ioredis adapter) без предварительной проверки `getRedis()` → `client.status === 'ready'`. Если Redis недоступен — in-memory fallback. Иначе `async error during store initialization` убивает **все** запросы через глобальный error handler (500 на каждом роуте).
17. **Admin Content — цепочка данных** — `admin-content.tsx` читает из `GET /api/content` (публичный), пишет в `PUT /api/admin/content/{section}`. Сервер читает ВСЕ колонки, заменяет ТОЛЬКО одну, пишет обратно. Запрещено: трогать `getContentConfig()` в `content.js`, удалять `invalidateContentCache()` после PUT, хардкодить banned-words для чат-модерации. Три отдельные системы banned-words: `content_config` (БД, чаты), `constants.ts` (хардкод, профиль), `groups.tsx` (хардкод, группы).
18. **handleSave внутри setState updater'а** — НИКОГДА не вызывать async side effects (fetch, save, API) внутри `setState(prev => {...})`. Паттерн: вычислить `next` из текущего state, вызвать `setState(next)`, потом `handleSave(next)` снаружи. Иначе React batching может отправить устаревшие данные.
19. **Autosearch: проверять формат ключей из разных источников** — данные из БД (`content_config`), demo-data, и фильтры могут хранить ключи в разных форматах (`interest.sport` vs `sport`). При сравнении — нормализовать. Город-фильтр: проверять и `"all"`, и `"Все"`.
20. **Dynamic import скрывает ошибки пропсов** — `dynamic(() => import(...))` не проверяет пропсы компонента. Если компонент требует 10 required props, а передано 3 — TypeScript молчит, кнопка крашится в рантайме. При динамическом импорте — всегда сверять пропсы по interface.
21. **bat-файлы: проверять все пути** — при копировании `запуск-всего.bat` между проектами/папками нужно обновлять ВСЕ `cd /d` пути, иначе MySQL/Node стартуют из несуществующей директории.
22. **Realtime-бан (этап 68): три корневые причины, почему WS-события не доходили** — (а) `@socket.io/redis-adapter`, прикреплённый к НЕподключённому Redis-клиенту (`lazyConnect`, `ECONNREFUSED`), делал `io.to().emit()` молча отвергнутым → события терялись. Фикс: `ws.js` вызывает `await isRedisReady()` (`redis.js`) и прикрепляет адаптер ТОЛЬКО если Redis реально ready, иначе in-memory; `index.js` — `await initIO(httpServer)`. (б) Vite не подхватывал `VITE_WS_URL` без перезапуска → клиент слал `ws://localhost:8081`. (в) CSP `connect-src` в `index.html` НЕ включал `ws://localhost:3002`/`http://localhost:3002` → браузер вообще не подключался к socket.io (console error: «violates the following Content Security Policy directive: connect-src»). Фикс: добавить origins в `connect-src`. После фиксов цепочка бана: админ → `user:banned` (emit + `disconnectSockets`) → клиент `use-websocket.ts` слушает и зовёт `logout()`. E2E `e2e/ban-realtime.spec.ts` сеет токен как global-setup + reload + ждёт POST `/api/auth/logout`.
23. **Admin Content — «высокие кнопки» при малом количестве элементов** — бейджи (Badge) в секциях выглядят «высокими», когда элементов мало, и «нормальными», когда много. Причины и решение (проверено вживую):
   - `flex flex-wrap` с дефолтным `align-items: stretch` + жёсткий `min-h-[120px]` раздували строку и рамку → при 2–7 бейджах висят в высокой коробке и кажутся высокими. Фикс контейнера: `flex flex-wrap items-start gap-2 p-4 rounded-2xl border bg-muted/30` БЕЗ `min-h`.
   - Длинные названия («Неоконченное высшее», «Серьёзные отношения») переносились на 2 строки → бейдж рос в высоту. Фикс бейджа: `text-xs py-0.5 px-2.5 rounded-full ... whitespace-nowrap leading-none`.
   - Количество само по себе НЕ меняет высоту — всё дело в stretch/min-h и переносе строк.
24. **Admin Content — добавление не сохранялось при обновлении** — `onAdd` менял только state в браузере; в БД писался только явный «Save». Пользователь ждал автосохранения. Фикс: в page-обработчиках `onAdd` считаем `next`, `setX(next)` и сразу `handleSave(section, next, setX)` (как в `onDelete`). Общий паттерн — в пункте про handleSave (compute `next` → `setState(next)` → `handleSave(next)`).
25. **Admin Content — content_config держала «плоские» строки вместо JSON** — секции (`interests`, `dating_goals`, `education`, `banned_words`) лежали как `"cars,architecture,..."` (не `["…"]`); серверный `parseJsonField` (`JSON.parse`) падал → API отдавал пусто/фолбэк. Лечится перезаписью секций через `PUT /api/admin/content/{section}` (сервер сам делает `JSON.stringify`). Читать/писать через node fetch (UTF-8), НЕ через PowerShell — он портит кириллицу в cp1251 → «????».
26. **CSRF double-submit — код готов, защита НЕ активна** — `server/src/middleware/csrf.js`: в `index.js` подключён ТОЛЬКО `app.use(csrf)` (раздача cookie `csrf_token` + роут `GET /api/auth/csrf`). Блокировка `csrfGuard` закомментирована — включить одной строкой `app.use(csrfGuard)` при выносе API на поддомен; тогда все мутирующие запросы обязаны нести заголовок `x-csrf-token` === cookie (double-submit). Токен в cookie НЕ HttpOnly (клиент должен его читать). Тесты — `server/src/__tests__/csrf.test.js`. Не дублировать `csrf` ещё раз в роуте — иначе каждый вызов генерирует новую куку (проверено вживую).
27. **HTTP 500 «Unknown column» — локальная БД отстала от миграций** — `/api/hangouts` падал с `Unknown column 'h.view_count'`: таблица `_migrations` кончалась на 048, колонка появилась только в 049. Проверка: `SHOW COLUMNS`/`SELECT name FROM _migrations`, фикс — `node database/migrations/migrate.js` (идемпотентно, применяет недостающие). Общее правило: при 500 на сервере сначала воспроизвести SQL и сверить схему с миграциями; при этом кода менять не надо.
28. **mysql2 auto-parse JSON-колонок (content_config.banned_words)** — если колонка имеет тип `JSON`, `mysql2` возвращает уже распарсенный **массив/объект**, а не строку. Двойной `JSON.parse(массив)` падает в `TypeError` → познания «before: 0» и затирание списка. Идемпотентный обход: `const cur = Array.isArray(val) ? val : JSON.parse(val)`.
29. **`/api/hangouts` отдаёт `{ items, total }`, а не массив (этап 112)** — числовая пагинация. 48. **Тест, который падает 1 прогон из 4 в полном suite и никогда в одиночном — это гонка в проде, а не «нестабильный тест» (30.09.2026, этап 22)** — `hangouts.test.tsx` «shows pagination and replaces feed when next page is clicked» проходил в одиночном прогоне и падал в полном (медленнее машина → больше реального времени между шагами теста). Причина оказалась в `hangouts.tsx:746-753`: эффект дебаунса поиска при **монтировании** безусловно ставил `setPage(1)` через 300 мс, поэтому клик «следующая страница» в первые полсекунды после открытия страницы **молча откатывался** на 1-ю. Шаблон дефекта шире любой страницы с пагинацией: **таймер, меняющий состояние фильтра/страницы, должен срабатывать по изменению значения, а не по таймеру при монтировании** — иначе первый же осознанный клик пользователя отменяется. Отличать «флак» от бага можно только временем: гонка воспроизводится **замедлением**, и одиночный прогон её не показывает. Правило: увидев падение, которое не воспроизводится в одиночном файле, не перезапускать прогон, а искать `setTimeout`/`debounce`/`setState` вне обработчика события и проверять, что он срабатывает только при реальном изменении входа (регресс-тест с ожиданием «прошло N мс, страница не сменилась»). **Обратная сторона того же класса — выдуманный или не перепроверенный «известный флак»:** в бэклоге стояло «известный флак `login.test.tsx` (утечка `mockImplementationOnce`)», и это не подтвердилось — `beforeEach` зовёт `mockFetch.mockReset()` (`src/test/login.test.tsx:42-45`), а `mockReset` снимает и невыбранную once-очередь; `mockImplementationOnce` в файле не встречается ни разу, есть два `mockResolvedValueOnce` (строки 66, 91), каждый при своём тесте, 4/4 прогона по 6 тестов зелёные. Хуже — журнал противоречил сам себе: пункт C3 называл это флаком, разбор K4 — гонкой. Правило: утверждение о баге или флаке в бэклоге — **гипотеза, пока не названы файл и строка**; перенося чужую диагностику (транскрипт сессии, чужой «финальный отчёт»), перепроверять её по коду, а не по имени теста.

53. **Пустое хранилище выглядит как рабочее, а IDOR-тест может быть зелёным на уязвимом коде из-за сдвига параметров (01.10.2026, этап 27)** — P0 #5 «нет списка активных сессий и отзыва по одной» на деле распался на три независимых дефекта, и каждый был бы не найден, если смотреть только на формулировку задачи. **(а) Пустая таблица засчитывается как реализованная функция.** `user_sessions` (`database/mysql_schema.sql:1308`) объявлена с колонками `ip_address`/`user_agent`/`expires_at` и **никогда не заполняется**: единственные обращения во всём `server/src` — `DELETE` в `gdpr.js:96` и список таблиц в `seed.js:180`. 54. **Ломка гейта, которая не ломает ничего, доказывает ровно ноль — и хуже всего, когда она выглядит как доказательство (02.10.2026, этап 28)** — новый гейт order-by-audit (пагинация обязана заканчиваться уникальным столбцом) проверен 44 ломками: 30 сняли замыкатель в живом коде, 14 выключали по одному правилу самого гейта. Первый прогон показал **«пропущено: 5»** — и почти все пропуски оказались не виной гейта, а моими собственными ошибками в том, *как* я его ломал. **(а) Замена условия на 	rue не снимает правило, а усиливает его.** Условие было if (!expr.includes('.') && keys.includes(...)) continue; подстановка 	rue вместо второго операнда превращала if (a && true) continue — то есть пропуск срабатывал **всегда**, а тесты оставались зелёными, потому что пропуск стал шире. Правило: снимать правило — значит заменять **всё условие** на alse, а не операнд на 	rue; иначе ломка фиктивна и «доказывает» обратное. **(б) ull || regex.exec(...) — это не поломка, а no-op.** const limitMatch = null || /\bLIMIT/.exec(sql) даёт тот же regex: снятие требования LIMIT не происходило вообще, и кейс «запросы без LIMIT больше не отсекаются» был зелёным по совершенно другому поводу. **(в) Маскирующая проверка прячется за другим правилом.** Снятие проверки «последний термин — агрегат» не ломало тест ORDER BY COUNT(id) DESC, потому что isUniqueColumn смотрит на **последнее слово** выражения и находил id в PRIMARY KEY: тест проходил по другой причине. Понадобился отдельный тест, где за агрегатом столбца-идентификатора нет (ORDER BY MAX(title)). Правило: **каждое правило гейта требует теста, который зеленеет только от его снятия**; если тест зеленеет и без него — он проверяет не то правило. **(г) Самая дорогая разновидность — ломка, которая ломает не то.** Скрипт снятия замыкателя вырезал om[1].length + om[2].length вместо om[0].length, из-за чего из ORDER BY al.created_at DESC, al.id DESC получалось l.created_at DESC,LIMIT 20 — **без самого ORDER BY**. Поймали **два теста в обе стороны**: «continue-on-error у соседнего шага не придирается» (точность) и «continue-on-error ПОСЛЕ `run:` — тоже находка» (полнота). Общее правило: **условие «я вышел за границу блока» пишется как «символ в первой позиции не пробел» (`/^\S/`), а не «непробельный символ после любого пробела»** — вторая форма всегда истинна и обнуляет разбор.

67. **«Гейт вызывается из CI» по подстроке переживает переименование джобы, а `continue-on-error` после `run:` не виден в окне строк выше (04.10.2026, этап 32)** — две ломки wiring-проверки дали зелёный гейт. **(а) Переименование:** проверка искала подстроку `check:docs` в файле workflow, поэтому `docs-canon:` → `docs-canon-disabled:` оставалось зелёным: строка `- run: npm run check:docs` на месте, джоба по-прежнему запускается, но человек, читающий workflow, такого вызова уже не находит — и это ровно тот случай «гейт доволен упоминанием» из питфолла 62. Лечится разбором по отступу: `getJobBlock(yaml, 'docs-canon')` обязан найти **джобу с ожидаемым именем**, и вызов гейта искаться **внутри неё**. **(б) Порядок ключей YAML:** шаг с `continue-on-error: true` **ниже** `run:` (порядок ключей в YAML произвольный) не попадал в «окно из 4 строк выше» — гейт оставался зелёным на шаге, который ничего не блокирует (питфолл 56). Лечится обходом **блока шага** от его начала (строка с `-`) до следующего элемента списка, а не окном строк. Плюс разделены два уровня: `jobAllowsFailure` (ключи джобы на своём отступе) и `blockAllowsFailure` (внутри шага) — иначе `continue-on-error` у постороннего шага красил бы проверку wiring.

68. **Гейт по документации обязан обходить `git ls-files`, а не дерево ФС — иначе чужие удаления его ломают, а чужие untracked-черновики он проверяет (04.10.2026, этап 32)** — в рабочем дереве было 6 файлов `Оценка kimi|qwen|qwen1|дипсик|дипсик1.txt` + `Финальная оценка проекта SwiftMatch.txt`, **отслеживаемых в git, но удалённых владельцем**; обход ФС их просто не увидит, а проверка «все отслеживаемые .md/.txt существуют» упала бы с ENOENT на чужой работе. Решение: список — `git ls-files`, отсутствующий файл даёт `[SKIP]` и печатается отдельной строкой (не ошибка), untracked-черновики не проверяются вообще. Две мелочи того же места: `git ls-files` **экранирует не-ASCII** (`core.quotePath`), и без `-c core.quotepath=false` кириллические имена приходят как `"\320\237..."` — файл выглядит несуществующим (второй раз в этом проекте, см. питфолл 47в); а список расширений в регулярке ссылок обязан включать `js` — с `tsx?` без `m?js` половина ссылок на код (`server/src/index.js`, `limiters.js`) молча выпадала из проверки существования.

69. **Проверка ссылки на файл из документа не должна требовать то, чего в CI нет (04.10.2026, этап 32)** — таблица канона в `Промты.txt` ссылается на `test/ИНВЕНТАРЬ-ТЕСТОВ.md`, а каталог `test/` — локальное зеркало в `.gitignore` (`.gitignore:45`), в индексе git его нет. Наивная «все ссылки должны существовать» дала бы **красный CI на честном коде**, а обойти это «убери ссылку» нельзя: это единственное место, где сказано, где лежит инвентарь. Решение — явный список известного зеркала `MIRROR_FILES`, и правило обратное: **любая ссылка, начинающаяся с `test/`, обязана быть в этом списке**, иначе находка («её не проверит ни existence-проверка, ни CI»). Общий принцип: гейт, который требует наличия локального артефакта, в CI краснеет на правильном состоянии репозитория — и его отключают, что хуже отсутствия гейта.

70. **Оправдание гейта по номеру строки протухает молча: код сдвигается, а список — нет (04.10.2026, этап 33, N5)** — `scripts/n-plus-one-audit.mjs` держал `JUSTIFIED` как «файл + номера строк». К моменту подключения к CI номера разошлись с кодом (`profile.js:463` и `hangouts.js:633,638` давно не содержали SQL), и гейт докладывал о **трёх «новых» N+1** — два из которых были не новыми, а сдвинутыми. Это худший вид поломки гейта: он красный по неверной причине, и реакция человека — дописать новые номера строк, то есть отключить проверку, не заметив этого. Лечение — **якорь `expect`**: оправдание обязано указать текст, который остаётся на этой строке; если текста там нет, гейт выдаёт отдельную находку «ОПРАВДАНИЕ ПРОТУХЛО» с цитатой того, что строка содержит сейчас. Плюс тест гейта, который требует наличия якоря у каждой записи с номерами строк (без него якорь можно снести тихо, и защита от роста превратится в ноль). Общее правило: **любой список исключений, привязанный к номеру строки, обязан проверять, что строка всё ещё та**; иначе исключение превращается в мусор, который читается как «всё проверили».

71. **Тест, повторяющий форму проверки вместо самой проверки, доказывает ноль (04.10.2026, этап 33)** — первые два теста на дрейф оправданий выглядели так: создать фикстуру, вручную повторить проверку «есть ли `expect` на строке» и убедиться, что фильтр вернул одну запись. Такой тест зелёный и на сломанной функции: он не вызывает `collectJustificationDrift` вообще. Лечение — **инъекция зависимости**: `collectJustificationDrift(srcDir, list)` и `audit(srcDir, list)` принимают список оправданий параметром, тест кормит их фикстурой и проверяет находку настоящей функции. Тот же приём даёт границу в обе стороны: одна фикстура обязана краснеть (иначе гейт ничего не ищет), а та же фикстура с корректной записью в списке — зелёной (иначе гейт не умеет оправдывать).

72. **Тест кода, который пишет в цикл, закрепляет сам N+1 (04.10.2026, этап 33)** — `server/src/__tests__/profile.test.js` утверждал `insertCalls).toHaveLength(2)` при двух интересах, а `hangouts.test.js` мокал `pool.query` по одному `mockResolvedValueOnce` на каждого получателя. Тесты были зелёные ровно потому, что код делал по запросу на строку, то есть **фикстура воспроизводила то, что создаёт тестируемый код**. После батчинга они стали красными — и это правильный сигнал: новые тесты фиксируют инвариант «N элементов → 1 INSERT», а не число N. Общее правило: **утверждение о числе вызовов БД в тесте должно быть независимо от размера входа** — иначе тест защищает производительность, а не поведение, и следующая оптимизация ломает его вместо того, чтобы её разрешить.

73. **Курсор пагинации по времени умирает на TTL-уборке: пустой ответ выглядит как «история кончилась» (04.10.2026, этап 34, N2)** — каноничный способ курсировать «вглубь» — `created_at < ?` или подзапрос «взять время по id». Здесь он неверен: сообщения с TTL удаляются фоновой уборкой каждые 10 секунд (`cleanup.js`), и строка, на которую ссылается курсор, может быть удалена между запросами. Тогда запрос возвращает **пустую страницу**, клиент честно показывает «старше ничего нет» — и пользователь теряет кусок истории, который ещё существует, без единой ошибки. Лечение: **курсор по `m.id`** (автоинкремент: порядок вставки совпадает с порядком времени, удалённый курсор просто отсекает ещё меньше строк). Общее правило: **в курсоре нельзя использовать то, что может исчезнуть**; идентификатор строки безопаснее времени, а любое `created_at`-сравнение в курсоре надо спрашивать: «а если этой строки уже нет?».

74. **Ответ-страница без признака «есть ещё» неотличим от «это всё» (04.10.2026, этап 34, N2)** — `GET /api/chats/:chatId/messages` отдавал массив без метаданных, и фронт грузил «что пришло». В чате длиннее лимита это выглядит как «история кончилась», хотя она просто обрезана: пользователь физически не мог прочитать старые сообщения, а диагностировать было нечем. Лечение: ответ — **объект `{ messages, has_more, next_before }`**, где `has_more` получается честно, а не «есть ещё?», из-за взятого на один ряд больше (`limit + 1` строк): «сервер вернул больше, чем просил клиент» — единственный признак, который нельзя выдумать. Общее правило: **список в ответе обязан нести признак продолжения**, иначе пагинация на клиенте невозможна в принципе, а `limit` молча превращается в обрезание.

75. **Курсор в состоянии расходится с тем, что на экране: второй скролл повторяет первый запрос (04.10.2026, этап 34, N2)** — первая версия подгрузки держала курсор в `useState` и обновляла его в обработчике загрузки. Тест на порядок зелёный, тест на «второй скролл» — тоже: курсор брался из ответа **первой** страницы, а не последней принятой, поэтому второй запрос уходил с тем же `before` и возвращал ту же порцию второй раз (в списке она появилась бы как дубли, а если порядок склейки «старые сверху» — просто тихо удваивался объём). Вывод: состояние, из которого берётся позиция постраничного чтения, **нельзя хранить отдельно от того, что уже показано** — они обязаны быть одной величиной. Здесь курсор выводится из массива подгруженного: пока история не подгружена, это `next_before` первой страницы, после — id самого старого подгруженного сообщения (он и есть `next_before` последней принятой страницы). Побочный эффект — исчез гоняющийся `useEffect` с `[messagePage, olderMessages.length]`, из-за которого тест падал в 1 прогоне из 4: `findByText` срабатывает на мутации DOM раньше, чем отработают пассивные эффекты.

76. **Недоеденная очередь `mockResolvedValueOnce` переживает `clearAllMocks` и делает тест зелёным по чужому остатку (04.10.2026, этап 34, N2)** — `social.test.js` добавил `pool.query.mockReset()` в общий `beforeEach`, и тест `POST /api/likes` сразу стал красным с 500. Оказалось, у него **не хватало одного значения** в очереди моков (роут делает 7 запросов, было заведено 6), и шестое-седьмое он годами добирал остатком очереди из предыдущего теста. В полном прогоне это всегда работает, в одиночном — нет, то есть зелёный результат держался на порядке объявления тестов. Лечение: `mockReset()` в `beforeEach` плюс **полная очередь в каждом тесте** — тест, который падает от честного сброса моков, был зелёным не по своей причине. Общее правило: **`clearAllMocks` чистит вызовы, но не очередь `...Once`**; тест, зелёный только в полном прогоне, проверяет не то, что кажется.

77. **`git checkout -- <файл>` откатывает не только ломку, но и незакоммиченную работу (04.10.2026, этап 34, N2)** — ломка гейта проверяется так: внести правку, прогнать, вернуть файл. Возврат через `git checkout --` уничтожает **всё**, что в файле не закоммичено, — включая основную правку этапа, если она ещё не в коммите (в этом эпизоде так и вышло: курсорная пагинация фронта была стёрта вместе с ломкой, пришлось восстанавливать шесть правок по памяти и заново прогонять тесты). Правильно: **снимок байтов в temp перед ломкой и запись байтов обратно** (скрипт делает это сам и печатает `идентичен`/`ОТЛИЧАЕТСЯ` в конце — сверка обязательна, иначе «откатил» и «забыл» неразличимы). Общее правило: **откат в эксперименте должен быть точной копией снимка**, а не командой, которая молча опирается на состояние индекса git.

78. **Гейт, сверяющий реальность с собственной константой, зелёный на настоящей дыре (04.10.2026, этап 35, N8)** — `scripts/secrets-leak-audit.mjs` проверял rsync-строку `deploy.yml` списком `['.env', '*.secret', '*.pem', '*.key', 'uploads']`: список лежит в коде гейта, и гейт проверяет, что эти пять строк есть. Всё, чего в списке нет, не проверяется вообще — поэтому `server/.jwt-dev-secret` (`.gitignore:32`), `.env.local`, `*.pfx`, `id_rsa` **ехали на VPS**, а гейт был зелёный три года. Дыра тут не в rsync, а в проверке: гейт знает, какие файлы считает секретами (`SECRET_FILE_RE`, 6 классов), и обязан сверять с этим знанием, а не с собственным перечислением. Лечение: список образцов имён (по одному на каждую ветку регулярки) и **вычисляемое покрытие** — «каждый образец обязан матчиться хотя бы одним `--exclude`». Общее правило: **обязательный список в проверке и список сущностей в проверяемой системе — одно и то же знание, а не два независимых**; дублирование даёт гейт, который не может упасть.

79. **Проверка «какие файлы лежат на диске» в CI зелёна по построению (04.10.2026, этап 35, N8)** — естественный способ закрыть N8 — обойти дерево и потребовать, чтобы каждый найденный файл-секрет был исключён из rsync. Это не работает: после `actions/checkout` незакоммиченных файлов в рабочем дереве **нет вообще** (`.env`, `.jwt-dev-secret` — в `.gitignore`), гейт нашёл бы ноль файлов и радостно стал зелёным на том же дефекте. Канал проверки обязан опираться на **классы имён**, известные и в CI: список образцов сверяется с шаблонами rsync, а не с файловой системой. Общее правило: **проверка, чей предмет проверки не попадает в CI, зеленеет по построению** — сначала спроси, существует ли этот предмет на машине, где гейт запускается.

80. **Семантика шаблонов rsync и docker противоположна; матчер с чужой семантикой зеленит сломанный workflow (04.10.2026, этап 35, N8)** — в `.dockerignore` `.env` исключает **только корневой** файл, а `**/.env` — все; в rsync наоборот, шаблон **без слеша матчит basename на любой глубине**, поэтому `.env` закрывает и `server/.env`, и не требует `**/`. Гейт написал мини-матчер с docker-семантикой (он уже был в гейте для `.dockerignore`) — и такой матчер объявляет `*.secret` покрытием `.jwt-dev-secret`, то есть **исправляет гейт, не чиня workflow**. Доказано прогоном B3: с matcher'ом по docker-семантике сам гейт **exit 0**, красны только тесты гейта. Общее правило: **семантика проверяемого формата выносится в отдельную функцию и фиксируется тестами на обеих противоположных парах** (`config/*.pem` не матчит `server/config/tls.pem`, `*.key` матчит `nested/dir/tls.key`); общий код для двух форматов — это не переиспользование, а способ сделать одну из проверок декоративной.

81. **`^` в регулярке без флага `m` привязан к началу всего блока, а не каждой строки — проверка «есть ли в блоке строка» молча всегда ложна (05.10.2026, этап 36, N1)** — проверка `npm test || true` была записана как `/^\s*(?:- )?run:.*\|\|\s*true/.test(code)`, где `code` — многострочный блок джобы из `ci.yml`. Без флага `m` `^` совпадает только с позицией 0, а блок начинается с `  test-server:` — проверка **никогда не срабатывала**, то есть джоба с `|| true` проходила гейт. Нашлось это не чтением кода, а падением теста: скрипт ломки искал подстроку и находил, гейт — нет. Общее правило: **регулярка с якорем `^`/`$`, применённая к блоку, обязана нести `m`; надёжнее — не полагаться на якорь вовсе** (`/continue-on-error:\s*true/` без якорей работает на любой строке), а тест гейта обязан содержать случай, где искомая строка стоит **внутри** блока, а не в начале.

82. **Ломка, бьющая по первому совпадению, а не по своей цели, остаётся зелёной и доказывает ноль (05.10.2026, этап 36, N1)** — ломка B1 вырезала блок `services:` из `ci.yml`, чтобы джоба `test-server` осталась без БД. Поиск шёл по `/^ {4}services:$/` по всему файлу и нашёл **джобу `e2e`** (она тоже объявляет сервис mysql) — изломался не тот объект, гейт остался зелёным, и «доказанная» ломка на самом деле ничего не доказала. Это второй случай одной грабли (питфолл 66) в новой обёрстке, и спасение только одно: **границы сущности вычисляются явно** (сначала найти блок джобы, потом искать внутри него). Общее правило: **пока не проверено «а тот ли это объект», ломка недействительна**, а зелёный результат ломки при исправном гейте — это не «гейт слишком строгий», а «ломали не то».

83. **`afterAll` выполняется даже после падения `beforeAll` — защита только в `beforeAll` прячет внятную ошибку под невнятную (05.10.2026, этап 36, N1)** — в `race.mysql.test.js` `beforeAll` получил явную проверку `if (!admin) throw new Error('MySQL недоступен по host:port')`, а `afterAll` остался прежним: `await admin.query(...)`. При недоступной БД вывод содержал **две** ошибки, и второй была `TypeError: Cannot read properties of null (reading 'query')` — первая, полезная, терялась в шуме, и читатель вывода не понимал, что произошло. Общее правило: **`skipIf` и проверки в `beforeAll` не отменяют `afterAll`**; каждая функция очистки обязана сама переживать то состояние, ради которого её писали, иначе диагностика теряется ровно в том прогоне, который её вызвал.

84. **Один и тот же «пропуск» честен локально и замаскирован в CI, если режим не объявлен флагом (05.10.2026, этап 36, N1)** — `describe.skipIf(!admin)` на машине без MySQL это удобство, а в джобе без сервиса БД — замаскированный ноль выполненных проверок: год зелёных джоб при полном пропуске единственного теста на настоящем движке. Попытка «просто убрать skipIf» ломает разработчика без локальной БД (`npm test` начинает падать), и такой гейт быстро отключают. Правильное решение — **режим по флагу окружения**: `REQUIRE_MYSQL=1` превращает пропуск в падение, локально флага нет и `npm test` зелёный. Общее правило: **тест, который умеет пропускаться, обязан иметь явный способ требовать себя**, а гейт обязан проверять, что этот способ включён именно там, где пропуск недопустим.

85. **Ломка, которая правит не то, чем задумано, всё равно «доказывает» гейт (05.10.2026, этап 37, N4)** — доказательство ломки B1 («код-валидатор шире CHECK») строилось так: строка файла бралась регуляркой, экранировалась через `replace(/[.*+?^${}()|[\]\\]/g, '\\$&')` — и **экранированная строка подставлялась обратно как замена**. В файл попали обратные слэши (`intField\(rawHeight...`), `findCodeRangeValidators` перестал видеть валидатор (в фактах было «код-валидаторов intField: 3» вместо 4), и гейт покраснел — но **по другой находке** («CHECK не проверяется кодом» вместо «валидатор разрешает 0..250»). Формально ломка сработала, по факту она доказала совсем другой класс дефектов, а настоящая проверка П1 осталась недоказанной. Общее правило: **доказательство ломки обязано утверждать не только «гейт красный», но и «красный по ожидаемой причине»** — сверять конкретный текст находки; иначе зелёный отчёт о ломках доказывает только то, что гейт где-то падает.

86. **Механическое отбрасывание окончания ломает английские слова (05.10.2026, этап 37, N4)** — `singular()` для связывания имён делал `word.endsWith('s') && !word.endsWith('ss') ? word.slice(0, -1) : word`, и `singular('status')` давал `'statu'`. Связь `HANGOUT_STATUSES` ↔ `hangouts.status` при этом ещё вытягивалась запасным правилом, но `wordsOf` засорнялся мусорными словами, а любое слово на `-us`/`-is` (`plus`, `analysis`) давало несуществующее. Общее правило: **морфология в гейтах — это словарь исключений, а не регулярка**: окончания `-us`/`-is` не трогаются, а сама функция обязана иметь тест на слова-ловушки (`status` → `status`, `categories` → `category`), иначе первый прогон на реальных данных падает в неочевидном месте.

87. **«Файл обращается к таблице» ≠ «список относится к этой таблице» — признак принадлежности, взятый из файла, даёт ложный класс находок (05.10.2026, этап 37, N4)** — первая версия гейта связывала именованный список кода с ENUM-колонкой так: «файл, где объявлен список, упоминает таблицу с такой колонкой». `hangouts.js` упоминает `partner_offers`, поэтому `HANGOUT_CATEGORIES` (категории встречи) проверялся против `partner_offers.category` (категории оффера) и давал находку «theater|exhibition|cafe|concert|sport|other», которой в проекте нет. Общее правило: **принадлежность объекта к сущности выводится из имени сущности или из близости операции записи, а не из факта, что они оказались в одном файле**; связь строится по словам имени (`validTags` ↔ `tag`, `type` ↔ `conversion_type`) и по расстоянию до `INSERT`/`UPDATE` в пределах фиксированного окна, а объединение значений нескольких кандидатов фиксируется как осознанное ослабление в тексте гейта.

88. **Проверка «объявлено, но не используется» без учёта экспорта объявляет живой список мёртвым (05.10.2026, этап 37, N4)** — счёт использований велся по файлу объявления, и `CHANNELS` из `notification-prefs.js` (экспортируется и читается в `routes/notifications.js` трижды) получал находку «список объявлен, но нигде не используется». Общее правило: **«используется» — это свойство репозитория, а не файла**: экспорт и импорт считаются применением, иначе гейт наказывает за модульность, а не за дыру.

89. **Покрытие ограничения, найденное по всем упоминаниям сущности, требует валидатор и там, где сущность только читается (05.10.2026, этап 37, N4)** — проверка «диапазонный CHECK покрыт кодом» искала писателей по `FROM`/`JOIN` вместе с `INSERT`/`UPDATE`, и на фикстуре падала с требованием валидатора в файле, который читает `user_profiles` ради ленты: ограничение защищает **запись**, читатель клиентский ввод не передаёт. Общее правило: **ограничение и проверка связаны через операцию записи**; «кто касается сущности» — слишком широкое условие для гейта, который должен требовать проверку только там, где она влияет на данные.

## 3. Security Rules и абсолютные запреты

> Источник: `docs/AGENTS-security.md` (4.5 КБ). Навигация: [оглавление](#оглавление) · §1–§15

#### What to NEVER do (absolute bans)

- **Никогда** не коммитить `.env` с реальными секретами. `.env` в `.gitignore`, `.env.example` — в репо
- **Никогда** не оставлять `console.log` в продакшен-логике платежей, писем, авторизации. Использовать `req.log` (структурированный лог) или winston
- **Никогда** не добавлять `cors({ origin: '*' })` в веб-версии продакшена. Только для Capacitor (`native.ts` определяет режим)
- **Никогда** не использовать `fs.writeFile` для пользовательских загрузок без валидации пути. Только uuid имена, только `/uploads/` директория
- **Никогда** не возвращать `adminAuth` из активного в пассивный/blocking-режим и не снимать гейт `/api/admin` — это откроет админку без авторизации. `dev-login` в production возвращает 404 — не открывать его заново
- **Никогда** не хранить `refresh_token` в localStorage/Preferences без httpOnly альтернативы. (Сейчас проект использует Bearer в заголовке — это ок, но не добавлять новые sensitive токены в storage)

---

#### 🛡️ Security Rules (быстрый чеклист)

- `adminAuth` middleware — **ACTIVE** (с этапа 9): 401 без/невалидный токен, 403 не-админ. Единый гейт `app.use('/api/admin', ...)` в index.js; публичен только `GET /api/admin/features`; `dev-login` → 404 в production
- **ПРАВИЛО adminAuth (qwen #1, этап 37):** защита админ-эндпоинтов — ТОЛЬКО через active-check middleware `adminAuth` (сам валидирует JWT и роль, сам отвечает 401/403). ЗАПРЕЩЕНО: (а) пассивные проверки вида `if (!req.user) next()` без ответа; (б) ручные проверки `req.user.role !== 'admin'` внутри хендлеров вместо middleware; (в) обход/удаление единого гейта `app.use('/api/admin', adminAuth)`. Новые админ-роуты наследуют защиту автоматически; проверка при ревью: запрос без токена обязан вернуть 401 ДО логики хендлера
- Все SQL-запросы — prepared statements (`??` в mysql2). Никакой конкатенации строк.
- Server-side только uuid для имён файлов, ограничение 5MB, только image/*
- CORS: `*` для Capacitor (dev), env-переменная для production
- Sentry beforeSend: фильтрует authorization, cookie, email, IP
- Stripe webhook: `express.raw({ type: 'application/json' })` ДО express.json()
- JWT: 256-bit ключ, 7d expiry, Bearer header
- **Auth-модель (этап 28, ADR):** основной Bearer-токен хранится в sessionStorage (`src/lib/token.ts`) — стандарт для SPA; переход на httpOnly cookie отложен: требует CSRF-защиты, credentials:include во всех 80+ fetch и переписывания E2E. Включать только отдельным этапом с полным прогоном тестов. НЕ добавлять новые sensitive токены (refresh_token) в storage — они в httpOnly-недоступных местах или БД (refresh_tokens)
- Rate limit: `/api/auth/` 60 req/min, общий `/api/` 30 req/s
- Helmet: CSP, X-Frame-Options, X-Content-Type-Options, и др. security headers
- Request ID: UUID на каждый запрос, X-Request-Id в ответе
- Модерация чатов: проверка banned-слов при отправке сообщений
- Бан пользователя + WS `user:banned` (мгновенный разлогин)

#### Пользовательский текст (этап 34+)

Свободные текстовые поля юзера чистятся сервером через `stripHtml` из `server/src/sanitize.js` (profile PUT, register display_name, посты групп, сообщения чатов). Новый текстовый input = обязательно добавь stripHtml.

## 4. i18n и трансляционные ключи

> Источник: `docs/AGENTS-i18n.md` (3.4 КБ). Навигация: [оглавление](#оглавление) · §1–§15

#### Golden Rule: Never display raw translation keys

Every value displayed to the user MUST be wrapped in `t()`:

- Interests: `{t(interest)}` — key is `"interest.sport"`, displays `"Спорт"` (RU) / `"Sports"` (EN)
- Goals: `{t(profile.datingGoal)}` — key is `"goal.serious_relationship"`, displays `"Серьезные отношения"` / `"Serious relationship"`
- Zodiac: `{t(user.zodiac)}` — key is `"common.zodiac.leo"`, displays `"Лев"` / `"Leo"`
- Education: `{t(profile.education)}` — key is `"education.higher"`, displays `"Высшее"` / `"Higher education"`

#### Data format convention

All data stored in DB, localStorage, demo-data, and state MUST use **translation keys**, not Russian or English display strings:

| OK | NOT OK |
|---|---|
| `"interest.photography"` | `"Фотография"` or `"Photography"` |
| `"goal.serious_relationship"` | `"Серьезные отношения"` or `"Serious relationship"` |
| `"common.zodiac.leo"` | `"Лев"` or `"Leo"` |

This ensures:
1. `t()` can always find a translation in any language
2. Comparisons (e.g. autosearch filters) always match regardless of language
3. Adding a new language doesn't require changing data

#### Available translation keys

| Prefix | Defined in | Example |
|---|---|---|
| `interest.*` | `constants.ts` → `INTEREST_OPTIONS` | `"interest.sport"` |
| `goal.*` | `constants.ts` → `DATING_GOALS` | `"goal.serious_relationship"` |
| `common.zodiac.*` | `constants.ts` → `ZODIAC_SIGNS` | `"common.zodiac.leo"` |
| `education.*` | `constants.ts` → `EDUCATION_OPTIONS` | `"education.higher"` |
| `circadian.*` | `constants.ts` → `CIRCADIAN_RHYTHM_OPTIONS` | `"circadian.early_bird"` |
| `attach.*` | `attachment-styles.ts` | `"attach.style.secure.label"` |
| `chats.theme.*` | `chats.tsx` → `CHAT_THEMES` | `"chats.theme.romantic"` |

#### Data Rules (реализация)

- **Всё** в БД, localStorage, state — translation keys (`interest.sport`, не `"Спорт"`)
- UI-тексты обязательно через `t()` — ни один raw key не должен быть виден пользователю
- Сортировка translated-списков: `t(item).localeCompare(t(item2))`
- Новые сущности: key в `constants.ts` + запись в `language-context.tsx` (RU и EN)
- Исключение: админка и Sentry-логи — технические ID (`user_123`), не `t()`

#### Где лежат переводы

Реальная i18n-система — inline `translations` в `src/context/language-context.tsx` (RU-блок, затем EN-блок, объект закрывается в конце файла). `t()` ищет в `translations[language]`, фолбэк на EN, затем на ключ; `{key}`-подстановка через options.

> ВАЖНО: файлы `src/locales/ru.json`/`en.json` — ОСИРОТЕВШИЕ, никто их не импортирует. Добавлять ключи только в `language-context.tsx`.

При добавлении нового ключа всегда добавлять и RU, и EN. При добавлении контента в БД через админку — синхронизировать переводы (иначе админка покажет сырые ключи).

| `swagger.js` | Все новые роуты имеют JSDoc, авторизация через Bearer описана |

Ключи генерируются локально (`npx web-push generate-vapid-keys`) и в репозиторий не пишутся |

#### Pre-flight Checklist (перед каждым закрытием production-задачи)

Проверить **все** пункты, даже если задача казалась «только про фронт»:

##### 1. Security grep (30 секунд)
```bash
grep -rE "dev-secret|localhost:300[0-9]|password.*=.*$|JWT_SECRET.*=.*key" \
  --include="*.env" --include="*.ts" --include="*.js" \
  --exclude-dir=node_modules --exclude-dir=dist
```
Если нашлось — не коммитить. Сгенерировать `crypto.randomBytes(32).toString('hex')` и вынести в `.env.example` (без реальных значений).

##### 2. Конфигурационная консистентность

Все порты должны совпадать по цепочке:
- `server/.env` → `PORT=3002`
- `vite.config.ts` → `proxy: { '/api': 'http://localhost:3002' }`
- `capacitor.config.ts` / `src/lib/native.ts` → `VITE_API_URL` указывает на тот же хост
- `.env` (root) → `VITE_WS_URL`, `VITE_API_URL` для Vite dev-сервера

Несоответствие = 502 Bad Gateway на проде.

##### 3. База данных: миграции, не ALTER TABLE

Новые колонки добавляются через `database/migrations/`, а не ручным ALTER TABLE в консоли MySQL.
Если в руте используется новая колонка — она должна быть в `mysql_schema.sql` и в отдельном файле миграции.

Правило: `git diff` не должен содержать `ALTER TABLE` в `.js`/`.ts` файлах (только в `migrations/`).

##### 4. Платежный флоу (если touched Stripe)

- [ ] `STRIPE_SECRET_KEY` и `STRIPE_WEBHOOK_SECRET` в `server/.env` (не `sk_test_...` если задача про «live»)
- [ ] Убрать `mockFallback` из прод-ветки или завернуть в `if (process.env.NODE_ENV !== 'production')`
- [ ] Добавить idempotency key на `checkout.sessions.create`
- [ ] Webhook роут использует `express.raw({ type: 'application/json' })` перед `express.json()`
- [ ] Проверить цепочку: выбор тарифа → редирект на Stripe → success/cancel → подписка в `subscriptions` таблице

##### 5. Email / SMTP (если touched auth/notify)

- [ ] `server/src/mail.js` не содержит `console.log` как единственный транспорт в проде
- [ ] `.env` содержит `SMTP_HOST`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM` (или fallback на Mailgun/Resend API key)
- [ ] Регистрация с реальным email отправляет письмо (проверить через Mailtrap или логи)

##### 6. WebSocket reliability (если touched ws.js / use-websocket.ts)

- [ ] Сервер (`server/src/ws.js`) настроен `pingInterval: 10000, pingTimeout: 5000`
- [ ] Клиент (`src/hooks/use-websocket.ts`) имеет reconnect с exponential backoff (max 30s)
- [ ] Сообщения подтверждаются (ack) — иначе при обрыве мобильного интернета сообщения теряются
- [ ] `user:banned` event разлогинивает клиента без перезагрузки страницы

##### 7. File Upload Security (если touched /api/upload)

##### 11. Запись в БД — обязательный смоук на живой стойке

> Добавлено 30.09.2026 после этапа 19: 807 зелёных тестов, оба режима дрейф-аудита и миграция `birth_date` — а `PUT /api/profile/:id` продолжал отдавать 500 на любое сохранение.

## 7. Workflow из 5 этапов + шаблоны промтов

> Источник: `docs/AGENTS-workflow.md` (10.0 КБ). Навигация: [оглавление](#оглавление) · §1–§15

Каждая задача проходит 5 этапов:

#### Этап 0 — Чтение кода (Code Reading)
1. Найти все релевантные файлы по теме (grep/glob)
2. Прочитать текущую реализацию: импорты, типы, API-контракт
3. Понять архитектуру: data flow, кто вызывает, кто потребляет
4. Проверить существующие тесты — что уже покрыто
5. Если баг — воспроизвести условие (логи, тесты, curl)

#### Этап 1 — Планирование (Plan)
1. Определить границы задачи: что входит, что НЕ входит
2. Выбрать архитектурное решение (1-2 предложения)
3. Составить список изменений: какие файлы создавать/менять
4. Проверить консистентность: не сломает ли изменение соседние модули
5. Если production — прогнать Pre-flight Checklist

#### Этап 2 — Реализация (Implement)
1. Сначала типы/интерфейсы (TypeScript strict, никаких any)
2. Потом data layer (API, SQL, Context, Query)
3. Потом UI (презентационные компоненты без логики)
4. Потом связка (state management + side effects)
5. Каждый коммит — одна атомарная логическая единица
6. Conventional Commits: feat:, fix:, refactor:, test:, docs:, chore:

#### Этап 3 — Тестирование (Test)
1. Unit-тесты на новую логику (Vitest + RTL)
2. Интеграционные: API через curl/Playwright
3. E2E: критические user flows (регистрация → лайк → чат)
4. Проверка edge cases: пустые данные, ошибки, лимиты
5. `npx vite build` — сборка без ошибок
6. `npm run test` + `cd server && npm run test` — 0 failures
7. `npx playwright test` — 0 failures

#### Этап 4 — Верификация (Verify)
1. Проверить, что старые тесты не упали
2. Проверить консоль браузера — нет ошибок
3. Проверить Network tab — правильные статусы
4. Если production — Security grep (хардкодные секреты, порты)
5. Обновить документацию (context.txt, AGENTS.md, persona.md при необходимости)
6. `git push` только когда всё зелёное

## 8. Запуск, порты и что делать, если инфра умерла

> Источник: `docs/AGENTS-startup.md` (3.2 КБ). Навигация: [оглавление](#оглавление) · §1–§15

#### Startup

Run `запуск-всего.bat` to start everything:
1. MySQL via Laragon `mysqld.exe` (always check `mysql_upgrade` warnings before assuming it's broken)
2. API: `node server/src/index.js` (port 3002 — NOT 3001)

**Production-режим фронта (требование пользователя, сент 2026):** dev-server с HMR убран из запуска — холодная компиляция модулей делала первый заход в админку ~2.6 с («тупит приложение»). `запуск-всего.bat`/`запуск.bat` собирают `build` и поднимают `vite preview`. `vite.config.ts` содержит `preview.proxy` для `/api` и `/socket.io` (иначе preview отдаёт 404 на API). Для HMR-разработки фронт запускать вручную: `npx vite --port 8081 --host`. После любой правки `src/` нужен перезапуск `npx vite build` + рестарт preview (dist-папка кэшируется процессами).

**Server .env** is in `server/.env`: `PORT=3002`, `DB_HOST=localhost`, `DB_USER=root`, `DB_PASSWORD=`, `DB_NAME=swiftmatch`, `DB_SOCKET=/tmp/mysql.sock`, `JWT_SECRET=dev-secret-key`, `JWT_EXPIRES_IN=7d`, `ADMIN_EMAIL=admin@swiftmatch.app`
**Vite proxy** targets `http://localhost:3002` in `vite.config.ts` — must match server port.

#### Startup reminder

- After `git pull noutadm main` in `C:\swiftmatch1bd` (the run directory), also run `cd server && npm install` if new packages were added.
- Kill old node processes: `Get-Process -Name "node" | Stop-Process -Force`
- Start server: `cd C:\swiftmatch1bd\server && node src/index.js` — **обязательно из `server/`**: `import 'dotenv/config'` грузит `.env` относительно CWD; при запуске из корня `JWT_SECRET()` вернёт случайный секрет, все токены «сгорят» → 401 на всех эндпоинтах (проверка: `npm run check:ports` фейлит без JWT_SECRET в server/.env)

Первый E2E-прогон после холодного старта может дать флаки (vite компилирует модули) — retries: 1 локально, 2 в CI уже настроены.

## 9. Production Deployment

> Источник: `docs/AGENTS-deployment.md` (2.2 КБ). Навигация: [оглавление](#оглавление) · §1–§15

#### Подготовка
1. Вписать 7 ключей в `server/.env` (Stripe, SMTP, Sentry, S3, Redis, DB_PASSWORD, CORS_ORIGIN)
2. `npx vite build` — сборка фронта в `dist/`
3. `cd server && npm ci --production` — зависимости бэка

#### Варианты хостинга
| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| VPS (nginx + PM2) | Полный контроль | Ручное администрирование |
| Docker + VPS | Изолированно, healthcheck | Сложнее отладка |
| Railway / Fly.io | Простота, SSL | Меньше контроля |

#### Docker + VPS (рекомендованный путь для staging)
1. `.env` в корне: `DB_*`, `JWT_SECRET`, `CORS_ORIGIN`, `REDIS_URL`, ключи (Twilio/AWS/Stripe/OpenAI/Sentry).
2. `docker compose build && docker compose up -d` — поднимает `app` (миграции применяются автоматически при старте), `db` (mysql:8 + schema/миграции при первом volume), `redis`, `nginx` (:8080, статика из `dist/`), `prometheus` (:9090), `grafana` (:3001).
3. Миграции: `node database/migrations/migrate.js` выполняется в CMD образа перед сервером; идемпотентно (таблица `_migrations`), безопасен для существующей БД.
4. Healthcheck: `GET /health` (curl в образе, `USER node`), compose-зависимости ждут healthy `db`.
5. Нагрузочный тест: `k6 run scripts/k6/load-staging.js` (smoke) или `k6 run --env MODE=load --env STAGING_URL=https://… scripts/k6/load-staging.js` (100 VU, пороги p95<500ms и <1% ошибок).

#### Nginx essentials
```nginx
location /api {
```

На сервере настроен `cors({ origin: '*' })` — подходит для Capacitor.

| Функция | Назначение |
|---------|-----------|

- `GET /api/profile/:id` — 60s, сброс на PUT profile
- `GET /api/matches` — 30s per-user, сброс на POST like→match

- `CACHE_TTL` в `server/.env.example` (по умолчанию 60s)
- Включить: раскомментировать `REDIS_URL` в `server/.env`

#### MySQL Backup

##### Скрипт `scripts/backup-mysql.ps1`
- auto-detect mysqldump (8 путей)
- `cmd.exe /c` для вызова mysqldump (избежать проблем PowerShell с ANSI)
- retention 7 дней
- Размер файла в выводе
- Task Scheduler: ежедневно в 03:00

#### DB Migrations

- Новые колонки — через `database/migrations/`, НЕ ручным ALTER TABLE
- `database/migrations/migrate.js` — запуск миграций (таблица `_migrations`)
- Нумерованные .sql файлы (001_..., 002_..., etc.)
- `git diff` НЕ должен содержать `ALTER TABLE` в `.js`/`.ts` файлах (только в `migrations/`)
- Если в роуте используется новая колонка — она должна быть в `mysql_schema.sql` И в отдельном файле миграции
- Запуск: `node database/migrations/migrate.js`
- Перед написанием SQL в server routes — проверить колонки через `DESCRIBE table`. Схема в `mysql_schema.sql` может отличаться от реальной БД

#### Integration Thinking: компоненты не существуют в вакууме

Прежде чем создать файл, ответить на 3 вопроса:

1. **Кто его потребляет?**  
   Swagger без валидных JWT-схем — бесполезен для фронта. Docker без `/health` — убивается оркестратором. Nginx без `proxy_read_timeout` — убивает WS.

2. **Что произойдёт в 3 ночи, когда это сломается?**  
   Нет healthcheck → Kubernetes перезапускает контейнер каждые 2 минуты.  
   Нет Sentry → ошибка в Stripe webhook остаётся незамеченной 8 часов.  
   Нет логов → не воспроизвести баг.

3. **Как я проверю это без ручного клика?**  
   Если ответ «открою браузер и посмотрю» — плохо. Нужен curl/API call/тест.

#### Data & State Consistency (расширение правил переводов)

Всё, что касается new features, должно использовать translation keys:

- Новые интересы → `interest.new_thing` в `constants.ts` + `language-context.tsx`
- Новые статусы подписки → `premium.status.active`, не "Активна"
- Новые ошибки API → `error.stripe.webhook_failed`, не "Webhook error"

#### Environment-specific Logic

Любой `if (process.env.NODE_ENV === 'development')` или `if (!STRIPE_KEY)` с mock-fallback должен быть явно задокументирован:

```js
// server/src/routes/premium.js
const stripe = process.env.STRIPE_SECRET_KEY 
  ? new Stripe(process.env.STRIPE_SECRET_KEY) 
  : null;

// Если stripe === null — использовать mock. Это ОК для dev, но в prod

```

**Запрещено:** тихий fallback без комментария. Пользователь не должен платить реальными деньгами и попадать в mock.

#### Capacitor / Native-specific

- `src/lib/native.ts` перехватывает fetch. Любой новый API-роут должен работать через абсолютный URL (`VITE_API_URL`), иначе в APK запросы уйдут в `file:///api/...`

## 11. Runbook: ключи и их ротация

> Источник: `docs/runbook-keys.md` (9.8 КБ). Навигация: [оглавление](#оглавление) · §1–§15

> Этап 41. Порядок ротации каждого ключа, влияние на пользователей и проверка после замены.
> Правило: ключи НИКОГДА не попадают в git (`.env` в `.gitignore`, проверять `git status --ignored`).

#### Где живут ключи

| Файл | Что содержит | Кто читает |
|---|---|---|
| `server/.env` | Все серверные ключи | `node src/index.js` (dotenv) |
| `.env` (корень) | Только `VITE_*` | Vite при сборке (`npm run build`) |

**Важно:** `VITE_*` вшиваются в бандл на этапе сборки — после смены нужен `npx vite build` + деплой статики, а не только рестарт API.

#### Универсальный порядок для любого ключа

1. Получить новое значение у провайдера.
2. Вписать в `server/.env` (заменой старого значения).
3. Рестарт API: `Get-Process -Id (Get-NetTCPConnection -LocalPort 3002 -State Listen).OwningProcess | Stop-Process -Force; Start-Process node -ArgumentList "src/index.js" -WorkingDirectory "<repo>\server" -WindowStyle Hidden`
4. Проверка: `Invoke-WebRequest http://localhost:3002/health` → 200, затем целевой смоук из таблицы ниже.
5. Если ключ был скомпрометирован — сначала отозвать старый у провайдера, потом шаги 1–4.

#### По-ключево

##### JWT_SECRET
- **Влияние при простой замене:** все access-токены становятся невалидными мгновенно — пользователи разлогинятся (refresh-flow восстановит сессию тихо, кроме web где httpOnly cookie refresh остаётся валидным).
- **Ротация:** сгенерировать `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"` → вставить → рестарт.
- **Проверка:** логин через UI; `/api/profile/me` с новым токеном.
- **Graceful rotation (без разлогина всех) — рекомендуемый путь.** Access-токен живёт **24 часа** (`expiresIn: '24h'`), поэтому достаточно окна в 24ч, а не «ждать неделю». `server/src/middleware.js` → `verifyToken()` перебирает `[JWT_SECRET, ...JWT_SECRET_PREV]`; новые токены подписываются **только** текущим ключом, старые принимаются, пока старый ключ в списке.
  1. Сгенерировать новый ключ: `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`.
  2. В `server/.env` **заменить** `JWT_SECRET=` новым и **добавить** `JWT_SECRET_PREV=<старый ключ>` (несколько ключей — через запятую).
  3. Рестарт API (шаг 3 универсального порядка).
  4. Проверить логин новым ключом: `POST /api/auth/login` → 200; старый токен из лога входа **до** рестарта должен продолжать работать (`/api/profile/me` → 200).

#### N+5. `mysql_schema.sql` деградировал — пересоздание БД даст неполную схему (этап 77, 29.08.2026)

**Факт:** `database/mysql_schema.sql` = **62 таблицы**, живая БД = **73**. Все 62 есть в live, но **29 таблиц созданы только миграциями 006–042** и в schema.sql отсутствуют: `_migrations`, `audit_log`, `config`, `consent_log`, `data_erase_requests`, `date_checkins`, `emergency_contacts`, `experiment_assignments`, `experiments`, `fcm_tokens`, `hangout_*`, `partner_*`, `partners`, `push_subscriptions`, `refresh_tokens`, `sms_verification`, `user_aliases`, `user_verifications`, `webhook_events`.

**Почему «работает»:** server-юнит-тесты мокают `db.js` (`vi.mock('../db.js')`) — им не нужна реальная/полная схема. CI init `mysql < mysql_schema.sql` создаёт тестовую БД из неполной схемы; `schema-validate.mjs` сверяет БД **только против schema.sql** (не читает `migrations/`) → самосверка«62 vs 62» (self-fulfilling), дрейф миграционных таблиц не ловится.

**Риск 🔴:** пересоздание прод-БД строго из `mysql_schema.sql` или на новом хосте (`mysql < schema.sql`, как делает CI) даст **неполную схему** → роуты hangouts/partners/experiments/refresh_tokens/user_verifications/push/sms и др. упадут с «table doesn't exist». Реальный деплой переживает только потому, что работает с существующей БД, поверх которой 45 миграций уже применены (`node database/migrations/migrate.js`).

**Правило:** схему нового окружения создавать не из schema.sql, а **`schema.sql` (базис) + `node database/migrations/migrate.js`** (применяет 006–042). Опционально — регенерировать `mysql_schema.sql` из живой БД (mysqldump --no-data) и закоммитить, чтобы CI-ишница снова была эталоном.

#### N+4. Админка 500 на PUT/POST — тестовый артефакт PowerShell+curl (этап 77, 29.08.2026)

**Наблюдаемый симптом:** `GET /api/admin/*` → 200; `PUT/POST /api/admin/*` с непустым JSON → **500 "Internal server error"**; `{}` → 400 ("At least one"). Воспроизводился только при передаче тела через `curl.exe` из PowerShell 5.1.

**Диагностический вывод (этап 77):**
- Реальный стек из перенаправленного stdout вторичного инстанса: `SyntaxError: Expected property name or '}' in JSON at position 1` в `body-parser/json.js:92` — тело уже битое на входе в `express.json()`.
- **Причина — PowerShell 5.1 ломает embedded double-quotes в argv нативного `curl.exe`** (та же природа, что pitfall №47 «PowerShell + кириллица в API-тестах»). Код сервера исправен.
- **Доказательство:** на живом 3002 те же `PUT` через node `fetch` дают **200** (features/content/pricing). GET-админ-роуты — 200.

**Как правильно слать тело в API-тестах на Windows (не curl-инлайн):**
- Тело в файл (UTF-8 без BOM) → `curl.exe -X PUT --data-binary @file.json -H "Content-Type: application/json" URL`
- Или программно: node `fetch` (`fetch(url, {method, headers, body: JSON.stringify(obj)})`)
- Или `Invoke-RestMethod -Body ([byte[]]...)`

**Восстановление бана админа (если аудит забанил его):**
```sql
UPDATE users SET is_active=1 WHERE role='admin';   -- вернуть всех админов
```
`dev-login` должен вернуть `role: 'admin'`; `GET /api/admin/stats` → 200.

**Правила аудита админки (чтобы не навредить проду):**
- `PUT /admin/users/:id/ban` — НЕ слать на реальные id; использовать несуществующий (`999999`) или scratch-БД (иначе FK `moderation_log` / реальный бан).
- Для получения стека — запускать вторичный инстанс того же `index.js` на `PORT=3399` с перенаправлением stdout/stderr в файл, не трогая прод-error-handler.

#### N+3. Circuit breaker для внешних сервисов (этап 76, аудит kimi #6 / дипсик #4)

**Задача:** не копить очередь запросов к внешним API (Stripe/OpenAI/S3) при их недоступности/деградации.

- **Webhook'и (входящие)** — breaker неприменим (не исходящие вызовы); защита от повторов — идемпотентность/express.raw.

## 15. Прошлые ошибки проекта

> Источник: `docs/past-mistakes.md` (40.1 КБ). Навигация: [оглавление](#оглавление) · §1–§15

#### Previous fixes (do NOT repeat these mistakes)

##### 1. Port mismatch (502 Bad Gateway)
Vite proxy targeted `localhost:3001` but `server/.env` set `PORT=3002`. All API calls returned 502. **Fix:** `vite.config.ts` proxy target → `3002`.

##### 2. Feature flags not applied (admin features toggles useless)
`FeatureFlagsProvider` (`src/context/feature-flags-context.tsx`) read flags **only from Supabase** (`supabase.from('feature_flags')`). Since project uses MySQL, Supabase is absent → flags always default (all `true`). Admin toggles saved to API but had no frontend effect. **Fix:** Added API fallback — when no Supabase, fetch `GET /api/admin/features` and map response.

##### 3. Missing router in profile.js
`server/src/routes/profile.js` used `router.get(…)` but lacked `const router = Router()`. Caused crash on profile routes. **Fix:** Added Router import and instantiation.

##### 4. Missing banned-words.js
`server/src/routes/admin/content.js` imported `../../banned-words.js` which didn't exist. Caused 500 on content save. **Fix:** Created `server/src/banned-words.js` with default word list.

##### 5. use-premium.ts — UTF-16 encoding + recursion
`src/hooks/use-premium.ts` was saved in **UTF-16 BE** (cmd incorrectly saved it). Caused parse errors and infinite recursion crash. **Fix:** Rewrote file in UTF-8.

##### 6. chartData.slice crash on /admin
`admin-stats.tsx` called `chartData?.slice(…)` but `chartData` could be `null`. Chart container had no explicit width/height → Recharts complained. **Fix:** Added optional chaining and array guards for all chart data. Recharts warning remains cosmetic if container is zero-size on stateless server.

##### 7. Missing email infrastructure
No `nodemailer` or `mail.js` for verification emails, password reset, etc. Auth routes had placeholders. **Fix:** Created `server/src/mail.js`, added `nodemailer` to `package.json` (with `EMAIL_USER`, `EMAIL_PASS` env vars). Auth routes now send verification/log controllers.

##### 8. No WebSocket server
No socket.io for real-time features (chat, notifications). **Fix:** Created `server/src/ws.js` using `socket.io`, integrated into `server/src/index.js` (wraps `http.createServer`). Listens on same port 3002.

##### 10. Admin 500 errors — DB schema mismatches
`/api/admin/stats`, `/api/admin/photos/pending`, `/api/admin/reports` returned 500 because the code referenced columns that don't exist in the MySQL `swiftmatch` database:
- `users.online` → use `user_profiles.online` (stats)
- `user_photos.moderation_status` + `moderation_reason` — columns missing → added via ALTER TABLE
- `reports.evidence` — column missing → added via ALTER TABLE

**Lesson:** Before writing SQL in server routes, verify columns against `DESCRIBE table` output. The database schema in `database/mysql_schema.sql` may drift from what's actually deployed.

##### 11. LookingFor missing in profile-edit
`/profile/edit` had no UI for "кого ищу" (lookingFor). The data model had `lookingFor` but no form control. **Fix:** Added `<Select>` with Male/Female/Все options, saves to `profile.lookingFor`.

##### 12. Server needs npm install after git pull
When pulling new commits that add server dependencies (e.g. `express-rate-limit`, `socket.io`, `nodemailer`), run `npm install` in `server/` before starting. Missing deps cause `ERR_MODULE_NOT_FOUND`.

##### 13. MySQL 8.4 my.ini — invalid options block startup
Laragon's `my.ini` had `loose-component_reference_cache=OFF` and `skip_component_reference_cache=1` — both invalid in MySQL 8.4.3. Caused `Data Dictionary initialization failed`. **Fix:** Remove both lines.

##### 14. Migration `IF NOT EXISTS` not supported in MySQL 8.4

##### 31. Refresh-токены: ротация, семьи, лок-аут (этап 34, 22.08.2026)

WHERE family_id = ?`). НЕ удаляй использованные токены из таблицы — без строки с `revoked=1` детект переиспользования невозможен. Смена пароля (reset-password) и POST `/api/auth/logout-all` отзывают все семьи юзера.
