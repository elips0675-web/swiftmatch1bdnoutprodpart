## Гипер-краткое резюме (правила, которые нарушать нельзя)

- **Портики:** сервер **3002**, фронт **8081**, Vite proxy → `http://localhost:3002`. Несоответствие = 502.
- **Самоперезапуск OpenCode (агента) — это авто-обновление, а не порт и не Docker.** Если агент закрылся и открылся сам — обновляется версия; не «лечить» это `taskkill` по порту (в скриптах проекта убийства по порту нет). Детали — `docs/AGENTS-startup.md`.
- **TypeScript strict**, никаких `any`. Комментарии в коде НЕ добавлять.
- **Всё** в БД/state — translation keys, UI через `t()`. Ни одного raw key пользователю.
- **Все SQL** — prepared statements (`??`). Никакой конкатенации строк.
- **adminAuth ACTIVE** (401/403), единый гейт `/api/admin`, публичен только `GET /api/admin/features`.
- **Redis недоступен** → тихий in-memory fallback, никогда не падать 500 на всех роутах.
- **JWT_SECRET** — lazy getter `JWT_SECRET()`, устанавливать до `jwt.sign()` в тестах.
- **Перед «готово»** — `npx vite build`; перед коммитом — зелёные тесты.
- **Работа не живёт в незакоммиченном дереве. Чекпойнт после каждого блока.** Этап дробится на микроблоки. **После КАЖДОГО завершённого логического блока** — запись `Stage N.Y` в верху `«Что сделано.txt»`, `git add` поимённо, `git commit --no-verify -F`, `git push origin main`. Перед переходом к следующему блоку **обязателен** `npm run retent:check`; автоматизация той же механики — `npm run stage:checkpoint` (сверяет окно, пишет `Stage N.Y` в журнал, коммитит поимённо, пушит; на красном окне **ничего не трогает**). Переход запрещён при незакоммиченном окне **> 6 файлов / 300 строк**. Обратная подстановка (слом→красный→откат/фикс) заканчивается возвратом кода и **немедленным** коммитом+push. `npm run retent:check` (строгий 6/300), `--preflight` 10/450. Черновики владельца (`Анализ задание агенту.txt`, `Анализ тестов.txt`, `Оценка доработка дипсик1.txt`) не коммитятся и не считаются.
- **Дрейф схемы = живой 500.** Колонка, которую читает код, обязана быть и в `database/mysql_schema.sql`, **и создаваться миграцией**. Проверка: `node scripts/schema-drift-audit.mjs --offline` (без MySQL) и `node scripts/schema-drift-audit.mjs` (с живой БД, нужен `MYSQL_BIN`). Мок БД не доказывает, что колонка существует.
- **Ограничение в схеме = проверка в коде.** CHECK/ENUM из `database/mysql_schema.sql` отвечают 500, а не 400: клиент должен быть отбит кодом раньше. Правило: диапазонный CHECK обязан быть проверен в том файле, который **пишет** в таблицу (`intField(col,{min,max})` или ручное `< A … > B`), а белый список кода — не шире ENUM. Гейт: `npm run check:enum-constraints` (`scripts/check-enum-constraints.mjs`, джоба `enum-constraints` в `ci.yml` + шаг в `lint-and-typecheck` `deploy.yml`).
- **Mock-платежи = fail-closed.** `refuseMockPayment(res)` в проде и при `STRIPE_LIVE=true` отдаёт `503 {code:'STRIPE_NOT_CONFIGURED'}`, mock живёт только вне прод-контура. Новая платная точка (`server/src/routes/*.js`) не мержится без этого вызова: гейт `npm run check:prod-mock` (`scripts/prod-mock-audit.mjs`, джоба `prod-mock` в `ci.yml` + шаг в `lint-and-typecheck` `deploy.yml`) требует отказ в каждом хендлере с платным стоком (`mock: true`, `'paid'`, `INSERT INTO … subscriptions`, `commission_rate = 15`); вебхуки (`received: true`) — контракт Stripe, вне проверки. Фронт показывает отказ по `code`, а не сырое английское `message` (`premium.stripe_unavailable`, `partner.stripe_unavailable`).
- **Прод-зависимости = два lock-файла.** `npm run audit:prod` (корень) и `npm run audit:prod` в `server/` — exit 0 = нет high/critical. Флаги обязательны: `--omit=dev` (в образ едет только прод-часть) и `--audit-level=high` (иначе гейт красный от moderate/low, которые чинятся мажорными обновлениями). Гейт в CI блокирующий: джоба `dependency-audit` + шаги в `lint-and-typecheck` (`deploy.yml`).
- **Заголовки безопасности = периметр, а не middleware.** `helmet()` в `server/src/index.js` отвечает только за ответы Express; SPA и статику отдаёт **nginx** (`nginx/swiftmatch.http.conf` едет в образ, `Dockerfile`) и `vercel.json` — там заголовки обязаны быть продублированы. Правило nginx: если в `location` объявлен хоть один свой `add_header` (обычно `Cache-Control`), верхнеуровневые заголовки не действуют — каждый такой `location` повторяет полный набор, а `add_header` без `always` уходит только на 2xx. Гейт: `npm run check:headers` (`scripts/check-security-headers.mjs`, джоба `security-headers` в `ci.yml` + шаг в `lint-and-typecheck` `deploy.yml`).
- **Деплой = health-gate + автоматический откат.** `docker compose up -d --build` в `.github/workflows/deploy.yml` (джоба `deploy`) не проверял, поднялся ли сервис, и при падении миграции/schema-проверки прод оставался на новой версии до ручного вмешательства. Теперь: снимок работающих образов `swiftmatch-app:rollback`/`swiftmatch-web:rollback` **до** сборки (сборка переназначает только `:latest`), `docker compose up -d --build --wait` плюс проба тех же порта и пути, что `healthcheck` в `docker-compose.yml` (`curl -fsS http://127.0.0.1:3002/health`, цикл 30×5 с), и отдельный шаг `if: failure()` с `docker compose up -d --no-build --wait` возвращает `:rollback` со своей проверкой health. Чтобы откат был возможен, у `app` и `nginx` в compose обязателен `image:` (иначе имя образа зависит от имени проекта). Миграции не откатываются (forward-only) — восстановление из бэкапа (`docs/rollback-plan.md`, раздел 0). Гейт: `npm run check:deploy-rollout` (`scripts/deploy-rollout-audit.mjs`) связывает compose и `deploy.yml`; падает, если `--wait` убран, снимок `:rollback` снят после сборки, проба не того порта, откат без `--no-build` или без `if: failure()`. Истинный zero-downtime (без секунд 502 при пересоздании) требует двух реплик за nginx и заблокирован решением «single-instance» (in-memory лимитеры, `docs/rollback-plan.md`, раздел про rate-limit) — это не «не сделано», а зафиксированное ограничение.
- **Бэкап = восстановление данных, а не схемы.** Смоук `scripts/verify-backup.mjs` (шаг в джобе `server-test`) снимал дамп с `--no-data`: проверялась пустая схема, ни одна строка не сверялась, а самодельный разбор дампа по `;\n` и `catch {}` гасили ошибку восстановления — «резервная копия восстанавливается» числилось проверенным, не будучи проверенным (питфолл «пустое хранилище выглядит как рабочее»). Теперь смоук кладёт канарейку с «сложными» значениями (кириллица, кавычки, слэш, `;` + перевод строки), снимает дамп **с данными**, восстанавливает его реальным клиентом `mysql` в отдельную БД `…_verify_backup` и сверяет канарейку побайтово и число строк ядра с источником; `mysqldump`/`mysql` нет, дамп без `INSERT INTO`, таблицы ядра не созданы — это падение, а не пропуск. Гейт: `npm run check:backup-smoke` (`scripts/backup-smoke-gate.mjs`, джоба `backup-smoke` в `ci.yml` + шаг в `lint-and-typecheck` `deploy.yml`).
- **Логи контейнеров растут без предела — это и есть «Docker съел диск».** У каждого сервиса `docker-compose.yml` обязан быть `logging:` (json-file, `max-size` ≤ 100 МБ, `max-file` ≤ 10): по умолчанию json-file пишет `/var/lib/docker/containers/<id>/<id>-json.log` бесконечно, а `docker system prune` логи **работающего** контейнера не удаляет, поэтому файл не виден ни в одном отчёте Docker. Тому же гейту подчинены retention Prometheus (`--storage.tsdb.retention.time`/`.size`, иначе том `prometheus_data` растёт молча) и запрет prune-команд в workflow: `docker system prune -a`, `docker image prune -a`, `docker volume prune` уносят образ `:rollback` (единственную цель автоматического отката) и тома `db_data`/`uploads_data` — «освободили место» = откат физически невозможен, база и фото удалены. Гейт: `npm run check:compose-logging` (`scripts/compose-logging-audit.mjs`, джоба `compose-logging` в `ci.yml` + шаг в `lint-and-typecheck` `deploy.yml`). Диск WSL/Docker Desktop сам не сжимается: prune освобождает место **внутри** vhdx, а на хосте его возвращает только компактация (26.10.2026: 39.13 → 6.6 ГБ). Безопасный порядок — `docs/AGENTS-deployment.md`, «Диск и логи контейнеров».
- **Один источник правил.** Правила — только в `AGENTS.md` + `docs/AGENTS-*.md`; идеи 21–34 — в `docs/product-roadmap.md`; `Промты.txt` — указатель (таблица «тема → где правило»), а не копия; файлы `Промты*` правил не содержат (`Промты.txt` — указатель, `Промты общее.txt` — библиотека промтов для внешних моделей, `Промты тесты для ИИ агента.txt` — архив чужой сессии), карта «файл → роль» — `README.md` («Документация: что где правда»). Архивы (`context.txt`, `docs/roadmap.md`) несут в шапке дату среза и ссылку на канон. Гейт: `npm run check:docs` (`scripts/docs-canon-audit.mjs`, джоба `docs-canon` в `ci.yml` + шаг в `deploy.yml`). Написать правило в третий файл = вернуть дыру, которую закрыли в коде. Там же версии стека в таблицах (`README.md`, `project-context.md`, `docs/AGENTS-*.md`) сверяются с `package.json`, а упоминание удалённого `zod` — находка. Там же числа и ссылки сверяются с реальными файлами (а не с константами гейта): «N джоб `ci.yml`/`deploy.yml`» ↔ строки `runs-on:` в workflow, лимит загрузки в `docs/AGENTS-security.md`/`docs/AGENTS-production.md` ↔ литерал `fileSize` в `server/src/routes/upload.js`, «N нумерованных миграций» ↔ `*.sql` в `database/migrations/`, а `context.txt` (архив) в пошаговом `docs/AGENTS-workflow.md` — находка; отсутствие якоря — находка, а не пропуск.
- **Фича = флаг + DoD.** Новый публичный модуль не мержится без feature flag: флаг объявлен в `feature_flags` (`database/mysql_schema.sql:397-415`, колонки таблицы) и читается через `src/context/feature-flags-context.tsx`, управляется в `/admin/features` (дефолты разные — проверять по `defaultFlags`, не «off» по умолчанию). DoD фичи: флаг, тест, i18n ru/en, чистый `npm run check:console`, актуальный инвентарь тестов (`node scripts/test-counter-audit.mjs --fix`, затем вписать описание вместо заглушки «требует описания» — гейт её роняет). Перенос правила из Service Desk; у SwiftMatch это числилось «не сделано» в `docs/agenda-archive.md:1300`.
- **Пункт плана/аудита без `file:line`-цитаты не принимается.** Факт — только с файлом и строкой, открытыми и проверенными по коду; пересказ чужой оценки без чтения указанного файла — не факт (питфолл «ссылка на этап N проверяется не в том файле»).
- **Сначала фикс, потом тест.** Тест, фиксирующий баг, пишется после устранения причины и зелён с первого прогона; красный тест в коммите «чтобы потом добить» — это флак, а не покрытие.
- **После изменения кода — `npm run check:console`** (`scripts/check-console.mjs`): обход статических страниц живого preview (8081 + API 3002), console-ошибки/pageerror/5xx = FAIL, известный шум (Sentry/Supabase/Service Worker/CSP/429) отфильтрован по списку из `e2e/helpers/audit.ts`, отдельно ловится пустая страница и отсутствие русского текста. Локально, в CI не заведён — CI закрыт полным Playwright E2E.
- **Бюджет бандла — `npm run check:bundle`** (`scripts/check-bundle-size.mjs`): gzip **initial** JS ≤ 500 KB и initial CSS ≤ 40 KB; initial — все ассеты, на которые ссылается `dist/index.html` (entry + modulepreload), поэтому `vendor-*` и новые entry-чанки под гейт попадают, а ленивые чанки маршрутов — нет. ## Требования пользователя (обязательные, верить не могу)

1. **Всё запускается через `запуск-всего.bat`** из корня проекта: MySQL (Laragon, порт 3306) → API (3002) → фронт (8081) → открывает браузер. Пути в батниках **только относительные** (`%~dp0`) — хардкод `D:\...` или `C:\...` ломал запуск и давал «ошибку сохранения» в `/admin/content`.
2. **Frontend запускается в production-режиме** (`npx vite build && npx vite preview --port 8081`), НЕ dev-server с HMR. Причина: в dev первый заход в админку тормозил (горячая компиляция модулей, ~2.6 с), пользователь жаловался «тупит приложение и админка». `vite.config.ts` содержит `preview.proxy` для `/api` и `/socket.io` — preview работает как прод-сервер без on-demand компиляции. Если нужно HMR для разработки — запускать `npx vite` вручную.
3. **После тестов (E2E/k6) ничего не должно ломаться и не оставаться мусора.** E2E-юзеры регистрируются с префиксом `e2e_*`/`layout_*` и плодят дубли hangouts в ленте. Playwright `globalTeardown` удаляет их из БД после каждого прогона (FK CASCADE подчищает связи). Запускать `npm run test:e2e` без последующей чистки БД нельзя.
4. **`/admin/content` (http://localhost:8081/admin/content) должен сохранять без ошибок.** Причина бага была в том, что сервер не стартовал из-за хардкода пути в `.bat`; PUT-backend (`server/src/routes/admin/content.js`) работает корректно.
5. **Профиль (`/profile`, `/profile/edit`) должен редактироваться и сохраняться.** Два фикса (сент 2026): (а) в `server/src/routes/profile.js` маршруты `/api/profile/:id` (GET/PUT) были зарегистрированы ДО статических `/api/profile/aliases`, `/api/profile/verification`, `/api/profile/me` — Express ловил их как `id="aliases"` → 404. Перенес `:id`-роуты в конец файла; (б) в `src/pages/profile-edit.tsx` `handleSave` делал `fetch PUT` БЕЗ заголовка `Content-Type: application/json` (тело не парсилось → изменения не применялись, но тост «Сохранено» всё равно показывался) и без проверки `res.ok` (ложный успех при ошибке), а при пустом списке фото из БД страница не подгружала дефолтные фото и блокировала сохранение проверкой `photos.length === 0`. Теперь: PUT с заголовками, проверка статуса, тост ошибки вместо фейкового успеха, дефолтные фото подставляются если в БД их нет.
