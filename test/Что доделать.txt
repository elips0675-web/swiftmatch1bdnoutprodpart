## Правила работы с журналами и бэклогом

- **Бэклог ≠ история.** Новые закрытые пункты пишутся в `Что сделано.txt` (хроника этапов); из бэклога закрытый пункт удаляется — тела закрытых пунктов ловит гейт `backlog-closed-line`, тело под закрытым заголовком — `backlog-closed-body`. В бэклоге остаётся только заголовок-маркер без тела. Полная история прошлых срезов — в `docs/agenda-archive.md`.
- **Числа в шапках** — только прогоном `node scripts/test-counter-audit.mjs` (exit 0), не перепечаткой: гейтом покрыты 8 файлов — `README.md`, `project-context.md`, `test/ИНВЕНТАРЬ-ТЕСТОВ.md`/`test/README.md`/`test/project-context.md`/`test/Для анализа.txt` и шапки `Что сделано.txt` / `Что доделать.txt` (карта `DOCS` в `scripts/test-counter-audit.mjs`).
- **Зеркало `test/Что доделать.txt`** синхронизируется с корнем побайтово после каждой правки бэклога (`npm run check:mirrors --fix`; история `Что сделано.txt` в `test/` не зеркалируется: `test/` — компактный набор для внешнего AI-анализа).
- **Кодировка:** править файлы node-скриптами + `cmd /c "node ... > file 2>&1"`, затем читать файл (PowerShell ломает кириллицу).
- **Пункт без цитаты кода** (`file:line`-цитата, проверенная по коду) в бэклог не попадает. Дата проверки обязательна, объём ограничен: строка-пункт таблицы с ID без `ДД.ММ.ГГГГ` в колонке «Проверено» роняет `check:docs` (`backlog-item-verified`), как и раздувание бэклога сверх 1500 строк (`backlog-max-lines`).
- **Свежесть даты «Проверено» — по типу пункта, а не по возрасту.** Возраст даты ничего не значит: код-гейты перепроверяются **каждым прогоном** (их подтверждает сама зелень `test`/`check:*`, а не дата), внешние блокеры (ENV-01..04) не меняются без владельца, а пункты `⏳ Ждёт действий пользователя` нельзя «подтвердить прогоном» — подтверждения нет и не будет до ключей. Поэтому сквозного «гейта свежести» нет и не заводится; архив по одной дате — тоже (архивируется только то, что доказано кодом: закрытый пункт → `Что сделано.txt`).
- **Фича = флаг** (по умолчанию off, включение через админку); DoD: флаг + тест + i18n + `check-console` + актуальный инвентарь тестов.
- **Сначала фикс, потом тест:** тест, фиксирующий баг, пишется после устранения причины и зелён с первого прогона.

## 🟡 Дополнительно считаю нужным

Ниже — пункты, которые не являются “архитектурной катастрофой”, но по факту повышают шансы на стабильный продакшен и уменьшают риск “всё зелёное локально, но ломается на реальном окружении”.

### P2 — прод-hardening

- **P2-01: единый runbook запуска/перезапуска production стека.** Обязательно зафиксировать порядок: `docker compose up -d --build --wait`, проверка `/health`, `/api/admin/features`, `/api/account`, `mysqladmin ping`, `redis-cli ping`; проверка фактического соединения к БД/Redis и отсутствие “зеленого” статуса при лишь запущенном контейнере. Сюда же — безопасный rollback по шагам и ручная проверка после деплоя.
- **P2-02: явная политика CORS + CSP + HSTS для реального домена.** Сейчас проект уже проверяет заголовки на уровне конструкций и nginx; но на живом домене нужно зафиксировать final policy для `site`, `api`, `ws`, blob/asset origins, а также правила для `Content-Security-Policy`, `Referrer-Policy`, `Permissions-Policy` и `Strict-Transport-Security`.
- **P2-03: жёсткая проверка пользовательского контента до публикации.** Сюда входят: sanitization HTML/URLs, лимиты на длину текста/фото, запрет содержимого с HTML/JS, ограничения на `message`, `bio`, `group description`, `hangout title`, `offer text` и проверка загрузки изображений «под реальный размер» до сохранения в S3/MySQL.
- **P2-04: отдельный smoke-check для токенов/сессий и refresh race.** Невозможно оставить только unit-тесты: нужен короткий сценарий на реальном окружении с длительным access-token, refresh, блокировкой/повторным запросом, истечением `JWT` и проверкой запроса без падения UI.
- **P2-05: унификация логов критического фронта и backend.** Все `console.*` в production должны быть либо отсутствовать, либо отправляться в Sentry/structured log с уровнем; критичные ошибки (Stripe fail, Redis fail, websocket fail, upload fail, auth fail) должны иметь явные метки и человеко-читаемую причину, чтобы не теряться в продовом трафике.

### P3 — UX / релиз-подготовка

- **P3-01: final release checklist для App Store / Google Play / web.** Нужно зафиксировать: домены, app links, signed build, key alias, screenshots, privacy policy, terms, 17+ warning, app metadata, versioning, release notes, rollback criteria.
- **P3-02: финальный smoke по реальным ключам для платежей и push.** После ENV-01 нужно не только “сборка проходит”, но и один живой сценарий: оплата, webhook, webhook verification, push permission, delivery to device, failure path in UI.
- **P3-03: синхронизация документации с действительным release-режимом.** В README/project-context/AGENTS и deploy-статьях должно быть только то, что реально проверено на этом окружении; все “mock-only” и “fallback-only” пути должны быть явно отмечены как не-production.
- **P3-04: проверка загрузки и хранения фото в S3/объектном хранилище.** Не только API работает локально, но и реальные ссылки на фото, ресайз/сжатие, cleanup dead files, retention, и purge после удаления профиля/публикации должны быть проверены.
- **P3-05: минимальный наблюдаемый SLA.** Нужен список SLO/SLA на уровне продукта: uptime, p95 latency для API, p95 для websocket, error rate, recovery time after deploy, dead-letter queue monitoring.

### P3 — технический долг, который очень легко забыть

- **P3-06: очистка “магических констант” и разрешённых значений.** Список разрешённых типов, лимитов, статусов, временных интервалов должен быть один источник правды; сейчас в проекте явно есть такие дубли по UI, API и SQL.
- **P3-07: один canonical check для release branches.** Перед релизом должен быть один короткий чек-лист: `npm run test:coverage`, `npx vite build`, `npm run check:console`, `npm run check:bundle`, `npm run check:headers`, `npm run audit:prod`, `npm run check:env`, `docker compose config`.
- **P3-08: безопасность на уровне данных.** Периодически проверять: что не попадает в логи, не хранится в localStorage без необходимости, все HTTP-параметры проверяются в сервере, и нет открытых API-методов без auth/feature flag.
