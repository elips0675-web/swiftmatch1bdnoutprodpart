# Итеративный подход к задачам (5 этапов)

Каждая задача проходит 5 этапов:

## Этап 0 — Чтение кода (Code Reading)
0. Прочитать канон, а не пересказы: `AGENTS.md` + профильные `docs/AGENTS-*.md` (`docs/AGENTS-production.md` — для production-задач). Правила не искать в `Промты*` (см. `AGENTS.md`).
1. Найти все релевантные файлы по теме (grep/glob)
2. Прочитать текущую реализацию: импорты, типы, API-контракт
3. Понять архитектуру: data flow, кто вызывает, кто потребляет
4. Проверить существующие тесты — что уже покрыто
5. Если баг — воспроизвести условие (логи, тесты, curl)

## Этап 1 — Планирование (Plan)
1. Определить границы задачи: что входит, что НЕ входит
2. Выбрать архитектурное решение (1-2 предложения)
3. Составить список изменений: какие файлы создавать/менять
4. Проверить консистентность: не сломает ли изменение соседние модули
5. Если production — прогнать Pre-flight Checklist

## Этап 2 — Реализация (Implement)
1. Сначала типы/интерфейсы (TypeScript strict, никаких any)
2. Потом data layer (API, SQL, Context, Query)
3. Потом UI (презентационные компоненты без логики)
4. Потом связка (state management + side effects)
5. Каждый коммит — одна атомарная логическая единица
6. Conventional Commits: feat:, fix:, refactor:, test:, docs:, chore:

## Этап 3 — Тестирование (Test)
1. Unit-тесты на новую логику (Vitest + RTL)
2. Интеграционные: API через curl/Playwright
3. E2E: критические user flows (регистрация → лайк → чат)
4. Проверка edge cases: пустые данные, ошибки, лимиты
5. `npx vite build` — сборка без ошибок
6. `npm run test` + `cd server && npm run test` — 0 failures
7. `npx playwright test` — 0 failures

## Этап 4 — Верификация (Verify)
1. Проверить, что старые тесты не упали
2. Проверить консоль браузера — нет ошибок
3. Проверить Network tab — правильные статусы
4. Если production — Security grep (хардкодные секреты, порты)
5. Обновить документацию (AGENTS.md, persona.md и `docs/AGENTS-*.md` при необходимости); обновить `Что сделано.txt` + `Что доделать.txt` + синхронизировать зеркала в `test/` (`npm run check:mirrors`, побайтово); счётчики — `node scripts/test-counter-audit.mjs` (итерации с `--skip-e2e`, полный прогон один раз в конце — он идёт минуты и до конца молчит)
6. `git push` только когда всё зелёное

## Правило «не терять работу»: коммит после каждой части, а не в конце этапа

Долгий этап с единственным коммитом в финале — это окно потерь: если сессию
обрывает лимит, краш или чужая команда вроде `git checkout --`, пропадает **всё**
после последнего push, включая уже готовые прод-фиксы. Инцидент 21.10.2026
(Stage 146): дерево держало отключённый фикс (обратная подстановка оставляет код
сломанным) и 18 незакоммиченных файлов; обрыв в этот момент откатил бы прод-фикс.

Как правильно (обязательно):

0. **Чекпойнт — после каждого логического блока, а не в конце этапа.** Точный
   алгоритм (6 шагов) и жёсткие ограничения — в следующем разделе. Ниже — общие
   правила, которые он не отменяет.

1. **Дроби этап на части, каждая часть коммитится и пушится.** Как только часть
   логически завершена и её тесты зелёные — `git add <эти файлы>` →
   `git commit --no-verify -F <msg>` → `git push origin main`. Следующая часть —
   следующая запись `Stage N` в «Что сделано.txt».
2. **Обратная подстановка (слом → красный → откат) заканчивается возвратом кода
   и немедленным коммитом**, а не «оставлю до конца этапа». Сломанное состояние
   в дереве живёт секунды, не часы.
3. **Коммить только касающиеся части файлы** (`git add` поимённо), чтобы
   чужая незавершённая работа не уехала в сообщение. Исключение — согласованный
   счётчиковый/зеркальный блок: его коммитят вместе с частью, иначе CI
   `test-counters` краснеет на свежем клоне (числа в доках считаются по всему
   дереву, а untracked-файл в репо отсутствует).
4. **Никогда не коммитить** `.env` с секретами и владельческие черновики
   (`Анализ задание агенту.txt`, `Анализ тестов.txt`) — они остаются untracked.

Гейт (это правило, в отличие от «пиши чаще», можно сломать молча — поэтому оно
машинное):

- **`npm run retent:check`** (`scripts/retention-gate.mjs`) — считает
  незакоммиченное окно офлайн по git: изменённые файлы + строки из
  `git diff --numstat HEAD`, untracked — длиной файла. Порог **6 файлов / 300
  строк**, строго сверху. Плюс владельческие черновики из списка
  `IGNORED_UNTRACKED` в счёт не идут.
- **`npm run retent:check -- --preflight`** — мягкий порог **10 файлов / 450
  строк** для старта этапа (в него же завернута проверка `stage:preflight`:
  работа предыдущего этапа, не уехавшая в push, не даст начать новый).
- Красный гейт — не «стиль», а сигнал: разбей работу на части и закоммить.
  Гейт ничего не удаляет и не коммитит сам (как и `stage:facts`) — коммит
  остаётся осознанным действием.

## Чекпойнт после каждого этапного блока (обязательное)

**Правило:** после завершения ЛЮБОГО логического блока работы ты обязан сделать микрокоммит + push, не дожидаясь конца всего Stage.

«Логический блок» — это:
- новый скрипт + тест к нему
- фикс бага (воспроизведение + правка)
- правка гейта/правил
- обновление доков, затрагивающее канон
- мелкий рефакторинг, после которого код собран/протестирован

### Алгоритм чекпойнта
1. **Сверка окна** — `git diff --name-only HEAD && git diff --stat HEAD`
2. **Проверка гейта окна** — `npm run retent:check`. Если красный — НЕ добавлять новые правки, сразу дробить коммит
3. **Фиксация в журнале** — короткая запись `Stage N.Y` в верху `Что сделано.txt` (только суть, без подробного пересказа)
4. **Коммит поимённо** — `git add <список файлов>` (никогда `git add .`), `git commit --no-verify -F <файл-сообщения>`
5. **Push сразу** — `git push origin main`
6. **Быстрая валидация** — `node --check` по новым `.js/.mjs/.ts/.tsx`, при необходимости прогнать тесты затронутого модуля

### Жёсткие ограничения
- **Переход запрещён.** Нельзя браться за новый КРУПНЫЙ блок, пока незакоммиченное окно > 6 файлов ИЛИ > 300 строк. Сначала чекпойнт.
- **Исключение одно — механический счётчиково-зеркальный блок.** `node scripts/test-counter-audit.mjs --fix` + `node scripts/check-doc-mirrors.mjs --fix` переписывают числа в 8 доках и их зеркалах и трогают больше 6 файлов по определению. Этот блок **не дробится** (половинные числа = гейт красный) и коммитится целиком, отдельным коммитом сразу после блока, который изменил счётчики. Приоритет — «переход дальше», а не «пройти чекпойнт красиво»: лучше один широкий механический коммит, чем полусчётчики в восьми местах.
- **Рискованные действия — только на чистом/микроокне.** Перед `npm install/ci`, `git checkout --`, массовым поиском-заменой, правкой >3 файлов за раз — обязателен чекпойнт.
- **Обратная подстановка = немедленный коммит.** Если намеренно «сломал, чтобы показать красный тест», как только вернул рабочий фикс — коммит+push БЕЗ ожидания.
- **Только поимённый `git add`.** Особенно аккуратно с кириллическими именами (`Что сделано.txt`, `Для анализа.txt`).

## Рутина конца этапа (инструментарий, P2, закрыто 11.10.2026)

Вместо десятка ручных команд в конце этапа:

- **`npm run stage:facts`** (`scripts/stage-facts.mjs`) — один прогон: счётчики
  тестов (`test-counter-audit`), `tsc --noEmit`, `eslint` (root + server),
  `vite build` и все офлайн-гейты (`check:docs/enum-constraints/prod-mock/
  order-by/e2e/n-plus-one/env/env-parity/swagger-coverage/headers/mysql-race/
  ports`, `schema-drift --offline`, `check:mirrors`). Печатает готовый
  fact-блок для «Что сделано.txt» с честным статусом каждой проверки (✅/❌).
  **Ничего не редактирует** — коммит остаётся ручным. Флаги: `--skip-e2e`,
  `--fix` (передаются в счётчик), `--bundle` (check:bundle после build),
  `--network` (audit:prod root+server, check:deps), `--gate <имя>` (одна
  проверка). `check:console` не запускается никогда (нужны живые серверы).
- **`npm run stage:section "<Заголовок>"`** (`scripts/stage-section.mjs`) —
  каркас записи «Что сделано.txt»: заголовок с датой, `git diff --stat HEAD`,
  список новых (untracked) файлов, плейсхолдеры Задача/Что сделано/Ломка/
  Тесты/Проверки и чек-лист шапки «Что доделать.txt». Ничего не редактирует.
- **Структурный гейт бэклога** — внутри `scripts/docs-canon-audit.mjs`
  (`npm run check:docs`): каждый открытый ID (первая ячейка строк `| … |`)
  ровно один раз; заголовки `##`/`###` уникальны; нет `⏳` на строке с
  ✅/`ЗАКРЫТО`/зачёркиванием; в бэклоге не живут хронические заголовки
  «## … (ДД.ММ.ГГГГ): …»; каждая дата «ЗАКРЫТО …» обязана быть в
  «Что сделано.txt»; **у закрытого заголовка нет тела** (`backlog-closed-body`),
  **закрытых строк таблиц и пунктов в бэклоге нет** (`backlog-closed-line`)
  — надгробие с разбором этапа возвращает историю в бэклог; `docs/agenda-archive.md`
  обязан оставаться архивом; публичный `CHANGELOG.md` обязан существовать в
  формате Keep a Changelog и ссылаться на «Что сделано.txt».
- **Разделение ролей журналов** (то же правило, структурно): «Что доделать.txt»
  — открытые пункты (+ заголовок-маркер закрытых, **без тела**),
  «Что сделано.txt» — хроника по датам, `docs/agenda-archive.md` — архив
  срезов, `CHANGELOG.md` — пользовательская сводка по релизам. Развёрнутая
  запись закрытия живёт **только** в «Что сделано.txt» с той же датой.

# Оценка и улучшение промтов

Перенесено из Service Desk (`repo/prompts.md`, секция «Оценка и улучшение промтов»).
Стек-специфичные примеры заменены на SwiftMatch, принципы сохранены.

## Пять способов испортить результат и как их закрыть

| Проблема | Почему так | Что писать в промте |
|----------|-----------|--------------------|
| Забывает начало промта | Промт 2000+ токенов, модель теряет хвост | Разбивать на 2–3 сообщения: сначала стек, потом схема, потом задача |
| Навязывает лишние зависимости | «анимация чисел» → `react-countup`, «crop аватара» → `react-image-crop` | Явно: «без новых библиотек, только CSS/нативные API» |
| Смешивает слои | Бэкенд и фронт в одном файле | «Сначала `server/src/routes/*.js` (Express + SQL), потом `src/pages/*.tsx` (React)» |
| Забывает edge cases | Нет empty state / ошибок сети | «Обязательно: empty state, error boundary, loading skeleton» |
| Кривые типы | `any` и рассинхрон с API | «Типы синхронизировать с роутом, `any` запрещён» |

## Правила «дай модели выход»

Модель охотно тащит библиотеку, если ты описал эффект («с анимацией», «с деплойем»,
«с превью»). Явно помечай необязательные части словом **skip** — иначе она реализует
их и сломает компонент:

```
Drag-and-drop календаря (опционально, skip) — если сомневаешься, обычные кнопки
```

## Опасные формулировки и их замена в SwiftMatch

| Опасная формулировка | Что сделает модель | Правильная замена |
|---------------------|-------------------|-------------------|
| «httpOnly cookie **или** localStorage (выбери» | Выберет localStorage — это XSS-уязвимость | «httpOnly cookie через `setAuthCookies` (`server/src/cookies.js`). Не менять на localStorage» |
| «автосохранение (debounce 2 сек) **или** кнопка» | Выберет одно наугад | Указать явно, что нужно; если оба — «и то, и другое» |
| «сортировка на бэкенде **или** на фронте (reduce)» | Сделает не там, где нужно | «Сортировка на бэкенде в SQL ORDER BY» / «на фронте в useMemo» |
| «группировка результатов» | Смешает слои | Всегда указывать слой явно |
| «файл-хранилище, multer» | Напишет `memoryStorage`, сломает большие файлы | «`multer.diskStorage` + лимит размера, иначе крупные файлы упадут в память» |
| «пагинация» | Забыет про `limit`/`offset` клампинг | «limit клампится в диапазон (напр. 1..100), offset неотрицательный» |
| «реалтайм-чат» | Сделает polling | «Socket.io: эмит на сервере + `use-websocket.ts` на клиенте. Polling не подходит» |

Стек проекта:

- i18n: собственный контекст src/context/language-context.tsx, доступ через t()

Требования к коду:

2. Все SQL — prepared statements (?), никакой конкатенации
3. UI-тексты — только через t('translation.key'), сырые строки пользователю запрещены
   (ключи добавляй в RU и EN одновременно в language-context.tsx)

6. Без новых зависимостей без явной необходимости
## Универсальный промт этапа (цикл, не привязанный к пункту очереди)

Промт ниже описывает **сам цикл этапа**, а не конкретный пункт бэклога: агент
сам берёт первый незаблокированный пункт из «Что доделать.txt» → «Очередь
этапов», сам дробит крупный объём на этапы и сам предлагает следующий шаг.
Конкретные Stage/числа порогов в промт не вписываются — они меняются каждый
этап, и вписанное число протухает молча (pitfall «оправдание гейта по номеру
строки»); их агент берёт из журналов на шаге 1.

```
Продолжаем SwiftMatch1 по очереди этапов из «Что доделать.txt».

Сначала, до любых правок:
1) Прочитай docs/AGENTS-production.md (Golden Rule: Production ≠ File Created) — обязательно.
2) Прочитай «Что доделать.txt» (раздел «Очередь этапов», строки 127–134) и хвост
   «Что сделано.txt» (последние 2–3 записи этапов): оттуда берёшь номер этапа,
   фактические числа покрытия и строку порогов — не из этого промта.
3) Прогони `node scripts/test-counter-audit.mjs --skip-e2e` — счётчики зелёные и
   совпадают с документацией.
4) `git status --short` и `git log --oneline -5` — дерево чистое, последний этап
   совпадает с журналом.

Задача этапа:
- Возьми первый пункт очереди, который не зависит от владельца (ключи, VPS,
  живой E2E на HEAD, диск E: — только упоминать, не трогать).
- Если пункт — крупный файл (десятки непокрытых веток, сотни строк), не бери его
  одним этапом: разбей на смысловые блоки по строкам непокрытых веток и делай
  по одному блоку за этап.
- Перед каждым блоком — свежий замер покрытия (список целей брать из файла,
  а не из промта: после предыдущего блока нумерация строк сдвигается).
- Если ветка defensive (недостижима без правки прода ради теста) — не
  преследовать: зафиксировать в журналах как «defensive, недостижима».

Правила этапа:
- Сначала фикс (если баг), потом тест; тест зелёный с первого прогона; красный
  тест в коммите не оставлять.
- Каждый тест проверить обратной подстановкой: сломать покрытую строку → тест
  красный → вернуть (файл побайтово равен HEAD, `git diff` пуст) → снова зелёный.
  Слом обязан РАЗЛИЧАТЬ ветки: подстановка, дающая тот же результат, ничего не
  доказывает — заменить на различающую.
- Пороги coverage только вверх, буфер «факт − 2 п.п.» (vitest.config.ts /
  server/vitest.config.js). Снижать нельзя, числа — из журналов, не отсюда.
- Мерю покрытие: `cmd /c "cd server && npx vitest run --coverage
  --coverage.reporter=json --coverage.reportsDirectory=./cov-tmp > cov.log 2>&1"`,
  затем вспомогательным скриптом читаю coverage-final.json; итоговая цифра — по
  `npx vitest run --coverage` (text-summary); временные папку и скрипты удалять.
- Кириллицу правлю только node-скриптами (не PowerShell inline). npx/npm — через
  `cmd /c`. Коммит — `git commit --no-verify -F <темп-файл>`; темп-файл исключать
  из `git add -A` и удалять после коммита.
- Комментарии в коде не добавлять. TS strict, никаких any.
- Флаки под нагрузкой полного прогона фиксировать как гонку по времени и

вопросом «что дальше?», хотя очередь уже записана в бэклоге.

## Правила синхронизации журналов (Что сделано / Что доделать)

- **Что доделать.txt** — канон-бэклог. При закрытии пункта удаляй его **целиком** (всю строку/блок, без хвостов, без комментариев и «подводных камней»). В нём держится только открытое; закрытое **никогда** не оставляется.
- **Что сделано.txt** — хронологический журнал закрытий (кто, что, где в коде, ссылки `file:line`, счётчики, гейты). Коротко и фактами, без «остатков» из бэклога.
- **Блокеры (ключи/VPS).** Блокеры указываются в `Что доделать.txt` в полной форме, и у каждого критичного пункта, завязанного на внешние ключи/VPS, помечается **как его можно прогнать без реальных ключей** (моки, флаги `REQUIRE_*`, smoke-тесты, fail-closed с проверкой, локальные заглушки). Блокеры не выкидываются — переписываются в сжатом виде с вариантом имитации.
- **Чистота закрытий.** При закрытии пункта: (1) удалить его из `Что доделать.txt` целиком, (2) добавить запись в `Что сделано.txt`. Никаких «остаточных» упоминаний закрытого в бэклоге.
- **Третьей копии журнала нет.** `Что доделать коротко.txt` удалён 18.10.2026: производная свёртка без гейта (гейт `check:docs` только пропускал её), которая расходилась с каноном и держала дайджест закрытого. Очередь — `Что доделать.txt`, история — `Что сделано.txt`; заводить производные копии бэклога заново не нужно.
