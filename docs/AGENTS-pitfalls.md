# Pitfall'ы (из опыта)

1. **Баланс скобок в JSX** — при редактировании вложенных колбэков (onClick, onKeyDown с `=> { ... {{ }} />`) всегда проверять, что количество `{` и `}` сходится. Каждый открывающий `{` требует свой закрывающий `}`.
2. **Сборка перед ответом** — перед «готово» запустить `npx vite build`. TypeScript не ловит синтаксические ошибки JSX — только Vite.
3. **Перезапуск Vite** — если упал, убить процесс на порту 8081 и запустить заново.
4. **Сортировка translated-списков** — по `t(item).localeCompare(t(item2))`, а не по сырому ключу. Русский алфавит не совпадает с порядком английских ключей.
5. **Не трогать CSS бейджей в admin-content.tsx** — только логика, не стили.
6. **Развод не баним** — «развод» в дейтинге легитимен. Блокировка даёт ложные срабатывания.
7. **vi.mock factory + hoisting** — `vi.mock()` hoist'ится выше `const`. Всегда использовать `vi.hoisted(() => vi.fn())`.
8. **jsdom constraint validation** — jsdom блокирует submit если required поле пустое или type=email невалидный. Всегда noValidate на формах с кастомной JS-валидацией.
9. **INTEREST_KEY_TO_ID и NAME_TO_KEY** в profile-edit.tsx — синхронизировать при добавлении новых интересов.
10. **JWT_SECRET lazy getter** — middleware экспортирует `JWT_SECRET()` (функцию), а не константу. Тестовые файлы должны устанавливать `process.env.JWT_SECRET` ДО вызова `jwt.sign()`, потому что в ES modules import выполняется раньше любого кода теста. Вызов `JWT_SECRET()` читает `process.env.JWT_SECRET` в момент вызова, а не в момент импорта.
11. **Vite 8 `build.rollupOptions` (не `rolldownOptions`)** — `rolldownOptions` невалидная опция в Vite 8. Capacitor-пакеты (`@capacitor/push-notifications`, `@capacitor/geolocation`) нужно исключать через `build.rollupOptions.external`, иначе Vite падает с 500 при трансформации.
12. **MySQL 8.4: `IF NOT EXISTS` для `ADD COLUMN`** — не поддерживается. Использовать `information_schema.COLUMNS` + PREPARE.
13. **`INT` vs `INT UNSIGNED` для FK** — `users.id` — `INT UNSIGNED`. Все внешние ключи должны совпадать по типу.
14. **Express route order** — специфичные роуты (`/api/profile/me`, `/api/profile/aliases`, `/api/profile/verification`) ДО параметризованных (`/api/profile/:id`). Реальный кейс (фикс сент 2026): GET/PUT `/api/profile/:id` были зарегистрированы ДО статических — Express ловил `GET /api/profile/aliases` как `:id="aliases"` → 404. Правило: `:id`/`:param`-роуты — в КОНЕЦ роутера.
15. **export/import — проверять именованный экспорт** — перед `import { X } from 'y'` убедиться, что `y.js` экспортирует `X` именно как named export (`export function X` / `export const X`), а не как обычную функцию. Обычная function без `export` = ReferenceError при импорте = сервер не стартует.
16. **Redis/внешние сервисы — без проверки не подключать** — никогда не использовать Redis-backed store (rate-limit-redis, ioredis adapter) без предварительной проверки `getRedis()` → `client.status === 'ready'`. Если Redis недоступен — in-memory fallback. Иначе `async error during store initialization` убивает **все** запросы через глобальный error handler (500 на каждом роуте).
17. **Admin Content — цепочка данных** — `admin-content.tsx` читает из `GET /api/content` (публичный), пишет в `PUT /api/admin/content/{section}`. Сервер читает ВСЕ колонки, заменяет ТОЛЬКО одну, пишет обратно. Запрещено: трогать `getContentConfig()` в `content.js`, удалять `invalidateContentCache()` после PUT, хардкодить banned-words для чат-модерации. Три отдельные системы banned-words: `content_config` (БД, чаты), `constants.ts` (хардкод, профиль), `groups.tsx` (хардкод, группы).
18. **handleSave внутри setState updater'а** — НИКОГДА не вызывать async side effects (fetch, save, API) внутри `setState(prev => {...})`. Паттерн: вычислить `next` из текущего state, вызвать `setState(next)`, потом `handleSave(next)` снаружи. Иначе React batching может отправить устаревшие данные.
19. **Autosearch: проверять формат ключей из разных источников** — данные из БД (`content_config`), demo-data, и фильтры могут хранить ключи в разных форматах (`interest.sport` vs `sport`). При сравнении — нормализовать. Город-фильтр: проверять и `"all"`, и `"Все"`.
20. **Dynamic import скрывает ошибки пропсов** — `dynamic(() => import(...))` не проверяет пропсы компонента. Если компонент требует 10 required props, а передано 3 — TypeScript молчит, кнопка крашится в рантайме. При динамическом импорте — всегда сверять пропсы по interface.
21. **bat-файлы: проверять все пути** — при копировании `запуск-всего.bat` между проектами/папками нужно обновлять ВСЕ `cd /d` пути, иначе MySQL/Node стартуют из несуществующей директории.
22. **Realtime-бан (этап 68): три корневые причины, почему WS-события не доходили** — (а) `@socket.io/redis-adapter`, прикреплённый к НЕподключённому Redis-клиенту (`lazyConnect`, `ECONNREFUSED`), делал `io.to().emit()` молча отвергнутым → события терялись. Фикс: `ws.js` вызывает `await isRedisReady()` (`redis.js`) и прикрепляет адаптер ТОЛЬКО если Redis реально ready, иначе in-memory; `index.js` — `await initIO(httpServer)`. (б) Vite не подхватывал `VITE_WS_URL` без перезапуска → клиент слал `ws://localhost:8081`. (в) CSP `connect-src` в `index.html` НЕ включал `ws://localhost:3002`/`http://localhost:3002` → браузер вообще не подключался к socket.io (console error: «violates the following Content Security Policy directive: connect-src»). Фикс: добавить origins в `connect-src`. После фиксов цепочка бана: админ → `user:banned` (emit + `disconnectSockets`) → клиент `use-websocket.ts` слушает и зовёт `logout()`. E2E `e2e/ban-realtime.spec.ts` сеет токен как global-setup + reload + ждёт POST `/api/auth/logout`.
23. **Admin Content — «высокие кнопки» при малом количестве элементов** — бейджи (Badge) в секциях выглядят «высокими», когда элементов мало, и «нормальными», когда много. Причины и решение (проверено вживую):
   - `flex flex-wrap` с дефолтным `align-items: stretch` + жёсткий `min-h-[120px]` раздували строку и рамку → при 2–7 бейджах висят в высокой коробке и кажутся высокими. Фикс контейнера: `flex flex-wrap items-start gap-2 p-4 rounded-2xl border bg-muted/30` БЕЗ `min-h`.
   - Длинные названия («Неоконченное высшее», «Серьёзные отношения») переносились на 2 строки → бейдж рос в высоту. Фикс бейджа: `text-xs py-0.5 px-2.5 rounded-full ... whitespace-nowrap leading-none`.
   - Количество само по себе НЕ меняет высоту — всё дело в stretch/min-h и переносе строк.
24. **Admin Content — добавление не сохранялось при обновлении** — `onAdd` менял только state в браузере; в БД писался только явный «Save». Пользователь ждал автосохранения. Фикс: в page-обработчиках `onAdd` считаем `next`, `setX(next)` и сразу `handleSave(section, next, setX)` (как в `onDelete`). Общий паттерн — в пункте про handleSave (compute `next` → `setState(next)` → `handleSave(next)`).
25. **Admin Content — content_config держала «плоские» строки вместо JSON** — секции (`interests`, `dating_goals`, `education`, `banned_words`) лежали как `"cars,architecture,..."` (не `["…"]`); серверный `parseJsonField` (`JSON.parse`) падал → API отдавал пусто/фолбэк. Лечится перезаписью секций через `PUT /api/admin/content/{section}` (сервер сам делает `JSON.stringify`). Читать/писать через node fetch (UTF-8), НЕ через PowerShell — он портит кириллицу в cp1251 → «????».
26. **CSRF double-submit — код готов, защита НЕ активна** — `server/src/middleware/csrf.js`: в `index.js` подключён ТОЛЬКО `app.use(csrf)` (раздача cookie `csrf_token` + роут `GET /api/auth/csrf`). Блокировка `csrfGuard` закомментирована — включить одной строкой `app.use(csrfGuard)` при выносе API на поддомен; тогда все мутирующие запросы обязаны нести заголовок `x-csrf-token` === cookie (double-submit). Токен в cookie НЕ HttpOnly (клиент должен его читать). Тесты — `server/src/__tests__/csrf.test.js`. Не дублировать `csrf` ещё раз в роуте — иначе каждый вызов генерирует новую куку (проверено вживую).
27. **HTTP 500 «Unknown column» — локальная БД отстала от миграций** — `/api/hangouts` падал с `Unknown column 'h.view_count'`: таблица `_migrations` кончалась на 048, колонка появилась только в 049. Проверка: `SHOW COLUMNS`/`SELECT name FROM _migrations`, фикс — `node database/migrations/migrate.js` (идемпотентно, применяет недостающие). Общее правило: при 500 на сервере сначала воспроизвести SQL и сверить схему с миграциями; при этом кода менять не надо.
28. **mysql2 auto-parse JSON-колонок (content_config.banned_words)** — если колонка имеет тип `JSON`, `mysql2` возвращает уже распарсенный **массив/объект**, а не строку. Двойной `JSON.parse(массив)` падает в `TypeError` → познания «before: 0» и затирание списка. Идемпотентный обход: `const cur = Array.isArray(val) ? val : JSON.parse(val)`.
29. **`/api/hangouts` отдаёт `{ items, total }`, а не массив (этап 112)** — числовая пагинация. Legacy-массив поддерживается на клиенте (`Array.isArray(data)`), НО для пагинации нужно `data.total`. `total` — `COUNT(*)` по тем же фильтрам (гео — через `ST_Distance_Sphere` в подзапросе). `totalPages = ceil(total / limit)` — НЕ подставлять `total` напрямую (баг «1 / 45» в кэш-ветке, этап 112).
30. **/hangouts: бесконечный скролл заменён числовой пагинацией (этап 112)** — `IntersectionObserver`-sentinel удалён, страница грузится «взамен» (`setItems(list)`, не append). Тесты/UI должны кликать `hangout-page-{N}`/`hangout-page-next`, а не ждать авто-догрузку. Если API временно вернул массив — `totalPages` останется 1 (пагинация скрыта, поведение как раньше).
31. **/search: кнопка «Открыть профиль» УБРАНА (сент 2026, по запросу пользователя)** — в карточке осталась только круглая синяя иконка `User` (`text-blue-400`) в ряду действий (X → Лайк → Чат → Профиль), обе ведут на `/user?id=N`. Текстовая кнопка «Открыть профиль» под рядом (`search.open_profile`) удалена из `src/pages/search.tsx`. История: кнопку удаляли (a740b65, 94f4a70), возвращали «как было» (69f292e, 6e8db4c), затем пользователь попросил убрать текстовую кнопку. При правках этой карточки согласовывать порядок/цвет/состав кнопок.
32. **Cookie-баннер перехватывает клики на /search** — всплывающий `fixed bottom-20 z-[100]` блок «Принять все» (cookie consent) перекрывает ряд действий под карточкой (в т.ч. кнопку «Профиль»/Лайк/Чат). В Playwright подобные клики требуют `Принять все` → `force` или закрытие баннера.
33. **k6 с одного IP упрётся в собственный `/api`-лимитер** — `makeApiLimiter` (`server/src/middleware/limiters.js`) = **600 запросов/мин на IP**. «Бласт»-прогон k6 (100 VU без пауз) с одного IP всегда упрётся в 429 как в анти-DoS: локальный замер (этап 113) — **367 894 запроса / ~4 905 rps**, из них 200 — 50.3%, 429 — 49.7%, **0 ошибок 5xx**, `http_req_failed 49.67%` — это ровно лимитер, а НЕ деградация ёмкости (p95 26.88ms). Для честного «k6 100 VU» с порогом `<1% errors`: pacing/think-time в скрипте под потолок 600/мин, либо k6 Cloud/несколько IP, либо мерить raw-capacity отдельно (напр. `/health` без лимитера). Лимитер под тест не поднимать — это защитный слой поверх `nginx 30r/s`. `DB_POOL_MAX 20` при этом НЕ узкое место: локальный бласт прошёл без ETIMEDOUT и краха mysqld.
34. **Autosearch «никого не находит» — префиксный несовпадение интересов (фикс `09a7420`)** — профиль (onboarding/profile-edit через `content_config`) хранит интересы с префиксом `interest.photography`, а `performAutosearch` (`src/pages/search.tsx`) нормализовал только интересы пользователя (`strip('interest.')`), сравнивая их с **НЕнормализованным** `selectedInterests` из `sessionStorage['autosearchFilters']` → `commonInterests` всегда 0. Кандидаты оставались, только если совпадала цель (`hasMatchingGoal`), при пустой `datingGoal` — 0 результатов. Фикс: нормализовать ОБЕ стороны (`normalizedSelectedInterests`). Общее правило: при сравнении интересов/целей всегда снимать префикс `interest.`/`goal.` у обеих сторон (продолжение пункта 19).
35. **fetch PUT без `Content-Type: application/json` = тихий no-op + ложный тост успеха** — в `src/pages/profile-edit.tsx` `handleSave` слал `fetch PUT` без заголовка: Express не парсил JSON-тело → изменения не применялись, но сервер отвечал 200 и UI показывал «Сохранено». Плюс не было проверки `res.ok`, а дефолтные фото не подгружались при пустой `photos` из БД → сейв блокировался. Фикс: заголовки + проверка статуса + тост ошибки + `getDefaultProfile(t).photos` при пустой БД. Вектор бага: 2 проблемы одновременно (тело не парсится И клиент не проверяет ответ).

47. **Счётчики тестов в документации устаревают молча: 807 прошедших тестов ничего не говорят о том, сколько их на самом деле (сент 2026, этап 22)** — `README.md`, `project-context.md` и `test/ИНВЕНТАРЬ-ТЕСТОВ.md` хранили числа, расходящиеся с прогоном (632/48 и 147/24 против фактических 715/52 и 179/25; E2E «208 тестов» против 150), причём число «208» было получено статическим подсчётом вхождений `test(` в спеках, а не прогоном. Хуже: неверные числа **перепечатывались дальше** — попали в чужую «Финальную оценку проекта», где на них уже строились выводы. Ни один гейт этого не ловил: дрейф-аудит смотрит колонки, `secrets-leak-audit` — артефакты, а число «тестов» в `.md` не проверял никто. Фикс: `node scripts/test-counter-audit.mjs` — **измеряет** (перезапускает vitest в корне и в `server/`, E2E считает `playwright test --list`, БД не нужна) и сверяет с пятью документами; `--fix` переписывает сам. Три ловушки самого гейта, каждая из которых тихо выключала проверку: (а) **`m.indices[g]` — абсолютные смещения во всём тексте**, а не внутри совпадения — подстановка по `m[0]` не портила текст, а дописывала новые числа в конец строки («24 файла» → «24 файлафайла24теста152»), починено вычитанием `m.index`; (б) **шаблон расширений `m?[jt]sx?`, а не `[jt]sx?`** — `.mjs` это `m`+`j`+`s`, и без `m?` тесты самих гейтов (`scripts/*.test.mjs`) выпадали из инвентаря, а гейт писал бы «нет строки в инвентаре» про файл, который в этом же файле инвентаря перечислен; (в) **`\w` в JS не покрывает кириллицу** — класс символов `[\wа-яё-]+`. И общий принцип проверки гейта: он обязан падать на прежней конфигурации (`git stash` на документацию → exit 1), иначе это декорация — гейт, который всегда зелёный, хуже отсутствующего, потому что снимает вопрос. Плюс: русские окончания в шаблонах — `[а-яё]*`, а не `[а-яё]+`, иначе гейт не находит строку ровно на правильном числе («1 файл», «1 тест»); сломанный многострочный шаблон гасит сразу все числа блока, поэтому claim'ы держатся однострочными. **Ограничение гейта, которое надо называть вслух:** он сверяет пять документов-отчётов, а журналы `Что сделано.txt` / `Что доделать.txt` **не проверяет** — это пересказ, а не отчёт о прогоне, и числа в них стареют первыми. Ровно это и повторилось через один этап (30.09): заголовок `Что доделать.txt` объявлял «Актуально, после этапа 22» с `867/867` и без упоминания уже закрытого этапа 23, хотя полный прогон давал 895/895. Правило: любое новое число сначала получается прогоном или гейтом и только потом вписывается в журнал руками, вместе с датой и числом пройденных гейтов.

48. **Тест, который падает 1 прогон из 4 в полном suite и никогда в одиночном — это гонка в проде, а не «нестабильный тест» (30.09.2026, этап 22)** — `hangouts.test.tsx` «shows pagination and replaces feed when next page is clicked» проходил в одиночном прогоне и падал в полном (медленнее машина → больше реального времени между шагами теста). Причина оказалась в `hangouts.tsx:746-753`: эффект дебаунса поиска при **монтировании** безусловно ставил `setPage(1)` через 300 мс, поэтому клик «следующая страница» в первые полсекунды после открытия страницы **молча откатывался** на 1-ю. Шаблон дефекта шире любой страницы с пагинацией: **таймер, меняющий состояние фильтра/страницы, должен срабатывать по изменению значения, а не по таймеру при монтировании** — иначе первый же осознанный клик пользователя отменяется. Отличать «флак» от бага можно только временем: гонка воспроизводится **замедлением**, и одиночный прогон её не показывает. Правило: увидев падение, которое не воспроизводится в одиночном файле, не перезапускать прогон, а искать `setTimeout`/`debounce`/`setState` вне обработчика события и проверять, что он срабатывает только при реальном изменении входа (регресс-тест с ожиданием «прошло N мс, страница не сменилась»). **Обратная сторона того же класса — выдуманный или не перепроверенный «известный флак»:** в бэклоге стояло «известный флак `login.test.tsx` (утечка `mockImplementationOnce`)», и это не подтвердилось — `beforeEach` зовёт `mockFetch.mockReset()` (`src/test/login.test.tsx:42-45`), а `mockReset` снимает и невыбранную once-очередь; `mockImplementationOnce` в файле не встречается ни разу, есть два `mockResolvedValueOnce` (строки 66, 91), каждый при своём тесте, 4/4 прогона по 6 тестов зелёные. Хуже — журнал противоречил сам себе: пункт C3 называл это флаком, разбор K4 — гонкой. Правило: утверждение о баге или флаке в бэклоге — **гипотеза, пока не названы файл и строка**; перенося чужую диагностику (транскрипт сессии, чужой «финальный отчёт»), перепроверять её по коду, а не по имени теста.

50. **Гейт по секретам, построенный на одном канале, тихо зеленеет, когда появляется второй (30.09.2026, этап 24)** — `secrets-leak-audit` (этап 20) смотрел на **ИМЕНА** файлов: что попадает в контекст образа и что стирает `rsync --delete`. 51. **Фикстура, которая подставляет значение, создаваемое самим тестируемым кодом, делает тест зелёным на сломанной ревизии (01.10.2026, этап 25)** — серверный тест перепроверки WS-токена строил сокет фикстурой `makeSocket({ token })`, которая **сама** клала `socket.token`, а в проде это делает строка `socket.token = token` в handshake-middleware (`ws.js`). 65. **Гейт «запрещённая формулировка» обязан исключать журналы поимённо — и исключение проверяется тестом, иначе список растёт молча (04.10.2026, этап 32)** — `Что сделано.txt` и `Что доделать.txt` **обязаны** процитировать неверное правило («6 мест требовали сделать защиту `/api/admin` необязательной — исправлены»), иначе нечем зафиксировать его закрытие. Значит запрет обязан иметь исключение, а исключение — быть коротким и проверяемым: `FORBIDDEN_EXEMPT_FILES` из двух имён + тест «журналы с цитатой зелёные» + тест «правило сформулировано не как маркер, а как запрет». Смежная ловушка того же гейта, найденная его же прогоном: **собственный запрет попадает на текст о самом запрете** — описывая правило, я дважды процитировал в `README.md` и `docs/AGENTS-pitfalls.md` ровно те сочетания, которые гейт ловит, и `npm run check:docs` покраснел на текущем дереве (2 находки в `README.md:162`, 2 в `docs/AGENTS-pitfalls.md`). Лечится **переформулировкой, а не ослаблением регулярки**: в правилах сочетание описывается через id правила (`admin-auth-passive`, `zod-version-claim`) или словами («слова-признака пассивности», «`zod` и номер версии»), а буквальные примеры живут в JSDoc-шапке и в `hint` самого гейта — `scripts/*.mjs` под обход `.md`/`.txt` не попадает. Отсюда вторая находка того же прогона: **id правила тоже обязан не совпадать с собственной регуляркой** — первый ярлык был просто именем пакета с дефисом и номером версии, то есть **ссылка «см. правило <ярлык>» снова давала находку**; пришлось переименовать ярлык в `zod-version-claim`, не трогая саму регулярку. Общий вывод: **запрещённую формулировку нельзя писать буквально нигде в правилах — даже чтобы рассказать о ней**, поэтому в этом питфолле старый ярлык намеренно не приведён: любое его написание здесь дало бы находку на самом себе. Регулярки, кстати, обязаны ловить варианты написания: правило `zod-version-claim` проверяет любой регистр и дефис между именем пакета и номером версии — саму регулярку и буквальные примеры смотри в `FORBIDDEN_PHRASES` и `hint` в `scripts/docs-canon-audit.mjs`, потому что любое их написание в правилах даёт находку на самом себе.

66. **Проверка «граница блока» регуляркой `/^\s*\S/` совпадает с ЛЮБОЙ отступной строкой — гейт возвращает пустоту на валидном YAML (04.10.2026, этап 32)** — разбор шага workflow искал начало элемента списка вверх от строки с `run:`, и условие выхода «строка без отступа» было записано как `/^\s*\S/`, что истинно для `        run: …`. Результат: `getStepBlock()` возвращал `null` на полностью корректном шаге, а гейт начинал требовать «вызов гейта не принадлежит шагу» — то есть проверка была зелёной ровно там, где должна краснеть. Поймали **два теста в обе стороны**: «continue-on-error у соседнего шага не придирается» (точность) и «continue-on-error ПОСЛЕ `run:` — тоже находка» (полнота). Общее правило: **условие «я вышел за границу блока» пишется как «символ в первой позиции не пробел» (`/^\S/`), а не «непробельный символ после любого пробела»** — вторая форма всегда истинна и обнуляет разбор.

67. **«Гейт вызывается из CI» по подстроке переживает переименование джобы, а `continue-on-error` после `run:` не виден в окне строк выше (04.10.2026, этап 32)** — две ломки wiring-проверки дали зелёный гейт. **(а) Переименование:** проверка искала подстроку `check:docs` в файле workflow, поэтому `docs-canon:` → `docs-canon-disabled:` оставалось зелёным: строка `- run: npm run check:docs` на месте, джоба по-прежнему запускается, но человек, читающий workflow, такого вызова уже не находит — и это ровно тот случай «гейт доволен упоминанием» из питфолла 62. Лечится разбором по отступу: `getJobBlock(yaml, 'docs-canon')` обязан найти **джобу с ожидаемым именем**, и вызов гейта искаться **внутри неё**. **(б) Порядок ключей YAML:** шаг с `continue-on-error: true` **ниже** `run:` (порядок ключей в YAML произвольный) не попадал в «окно из 4 строк выше» — гейт оставался зелёным на шаге, который ничего не блокирует (питфолл 56). Лечится обходом **блока шага** от его начала (строка с `-`) до следующего элемента списка, а не окном строк. Плюс разделены два уровня: `jobAllowsFailure` (ключи джобы на своём отступе) и `blockAllowsFailure` (внутри шага) — иначе `continue-on-error` у постороннего шага красил бы проверку wiring.

68. **Гейт по документации обязан обходить `git ls-files`, а не дерево ФС — иначе чужие удаления его ломают, а чужие untracked-черновики он проверяет (04.10.2026, этап 32)** — в рабочем дереве было 6 файлов `Оценка kimi|qwen|qwen1|дипсик|дипсик1.txt` + `Финальная оценка проекта SwiftMatch.txt`, **отслеживаемых в git, но удалённых владельцем**; обход ФС их просто не увидит, а проверка «все отслеживаемые .md/.txt существуют» упала бы с ENOENT на чужой работе. Решение: список — `git ls-files`, отсутствующий файл даёт `[SKIP]` и печатается отдельной строкой (не ошибка), untracked-черновики не проверяются вообще. Две мелочи того же места: `git ls-files` **экранирует не-ASCII** (`core.quotePath`), и без `-c core.quotepath=false` кириллические имена приходят как `"\320\237..."` — файл выглядит несуществующим (второй раз в этом проекте, см. питфолл 47в); а список расширений в регулярке ссылок обязан включать `js` — с `tsx?` без `m?js` половина ссылок на код (`server/src/index.js`, `limiters.js`) молча выпадала из проверки существования.

69. **Проверка ссылки на файл из документа не должна требовать то, чего в CI нет (04.10.2026, этап 32)** — таблица канона в `Промты.txt` ссылается на `test/ИНВЕНТАРЬ-ТЕСТОВ.md`, а каталог `test/` — локальное зеркало в `.gitignore` (`.gitignore:45`), в индексе git его нет. Наивная «все ссылки должны существовать» дала бы **красный CI на честном коде**, а обойти это «убери ссылку» нельзя: это единственное место, где сказано, где лежит инвентарь. Решение — явный список известного зеркала `MIRROR_FILES`, и правило обратное: **любая ссылка, начинающаяся с `test/`, обязана быть в этом списке**, иначе находка («её не проверит ни existence-проверка, ни CI»). Общий принцип: гейт, который требует наличия локального артефакта, в CI краснеет на правильном состоянии репозитория — и его отключают, что хуже отсутствия гейта.

70. **Оправдание гейта по номеру строки протухает молча: код сдвигается, а список — нет (04.10.2026, этап 33, N5)** — `scripts/n-plus-one-audit.mjs` держал `JUSTIFIED` как «файл + номера строк». К моменту подключения к CI номера разошлись с кодом (`profile.js:463` и `hangouts.js:633,638` давно не содержали SQL), и гейт докладывал о **трёх «новых» N+1** — два из которых были не новыми, а сдвинутыми. Это худший вид поломки гейта: он красный по неверной причине, и реакция человека — дописать новые номера строк, то есть отключить проверку, не заметив этого. Лечение — **якорь `expect`**: оправдание обязано указать текст, который остаётся на этой строке; если текста там нет, гейт выдаёт отдельную находку «ОПРАВДАНИЕ ПРОТУХЛО» с цитатой того, что строка содержит сейчас. Плюс тест гейта, который требует наличия якоря у каждой записи с номерами строк (без него якорь можно снести тихо, и защита от роста превратится в ноль). Общее правило: **любой список исключений, привязанный к номеру строки, обязан проверять, что строка всё ещё та**; иначе исключение превращается в мусор, который читается как «всё проверили».

71. **Тест, повторяющий форму проверки вместо самой проверки, доказывает ноль (04.10.2026, этап 33)** — первые два теста на дрейф оправданий выглядели так: создать фикстуру, вручную повторить проверку «есть ли `expect` на строке» и убедиться, что фильтр вернул одну запись. Такой тест зелёный и на сломанной функции: он не вызывает `collectJustificationDrift` вообще. Лечение — **инъекция зависимости**: `collectJustificationDrift(srcDir, list)` и `audit(srcDir, list)` принимают список оправданий параметром, тест кормит их фикстурой и проверяет находку настоящей функции. Тот же приём даёт границу в обе стороны: одна фикстура обязана краснеть (иначе гейт ничего не ищет), а та же фикстура с корректной записью в списке — зелёной (иначе гейт не умеет оправдывать).

72. **Тест кода, который пишет в цикл, закрепляет сам N+1 (04.10.2026, этап 33)** — `server/src/__tests__/profile.test.js` утверждал `insertCalls).toHaveLength(2)` при двух интересах, а `hangouts.test.js` мокал `pool.query` по одному `mockResolvedValueOnce` на каждого получателя. Тесты были зелёные ровно потому, что код делал по запросу на строку, то есть **фикстура воспроизводила то, что создаёт тестируемый код**. После батчинга они стали красными — и это правильный сигнал: новые тесты фиксируют инвариант «N элементов → 1 INSERT», а не число N. Общее правило: **утверждение о числе вызовов БД в тесте должно быть независимо от размера входа** — иначе тест защищает производительность, а не поведение, и следующая оптимизация ломает его вместо того, чтобы её разрешить.

73. **Курсор пагинации по времени умирает на TTL-уборке: пустой ответ выглядит как «история кончилась» (04.10.2026, этап 34, N2)** — каноничный способ курсировать «вглубь» — `created_at < ?` или подзапрос «взять время по id». Здесь он неверен: сообщения с TTL удаляются фоновой уборкой каждые 10 секунд (`cleanup.js`), и строка, на которую ссылается курсор, может быть удалена между запросами. Тогда запрос возвращает **пустую страницу**, клиент честно показывает «старше ничего нет» — и пользователь теряет кусок истории, который ещё существует, без единой ошибки. Лечение: **курсор по `m.id`** (автоинкремент: порядок вставки совпадает с порядком времени, удалённый курсор просто отсекает ещё меньше строк). Общее правило: **в курсоре нельзя использовать то, что может исчезнуть**; идентификатор строки безопаснее времени, а любое `created_at`-сравнение в курсоре надо спрашивать: «а если этой строки уже нет?».

74. **Ответ-страница без признака «есть ещё» неотличим от «это всё» (04.10.2026, этап 34, N2)** — `GET /api/chats/:chatId/messages` отдавал массив без метаданных, и фронт грузил «что пришло». В чате длиннее лимита это выглядит как «история кончилась», хотя она просто обрезана: пользователь физически не мог прочитать старые сообщения, а диагностировать было нечем. Лечение: ответ — **объект `{ messages, has_more, next_before }`**, где `has_more` получается честно, а не «есть ещё?», из-за взятого на один ряд больше (`limit + 1` строк): «сервер вернул больше, чем просил клиент» — единственный признак, который нельзя выдумать. Общее правило: **список в ответе обязан нести признак продолжения**, иначе пагинация на клиенте невозможна в принципе, а `limit` молча превращается в обрезание.

75. **Курсор в состоянии расходится с тем, что на экране: второй скролл повторяет первый запрос (04.10.2026, этап 34, N2)** — первая версия подгрузки держала курсор в `useState` и обновляла его в обработчике загрузки. Тест на порядок зелёный, тест на «второй скролл» — тоже: курсор брался из ответа **первой** страницы, а не последней принятой, поэтому второй запрос уходил с тем же `before` и возвращал ту же порцию второй раз (в списке она появилась бы как дубли, а если порядок склейки «старые сверху» — просто тихо удваивался объём). Вывод: состояние, из которого берётся позиция постраничного чтения, **нельзя хранить отдельно от того, что уже показано** — они обязаны быть одной величиной. Здесь курсор выводится из массива подгруженного: пока история не подгружена, это `next_before` первой страницы, после — id самого старого подгруженного сообщения (он и есть `next_before` последней принятой страницы). Побочный эффект — исчез гоняющийся `useEffect` с `[messagePage, olderMessages.length]`, из-за которого тест падал в 1 прогоне из 4: `findByText` срабатывает на мутации DOM раньше, чем отработают пассивные эффекты.

76. **Недоеденная очередь `mockResolvedValueOnce` переживает `clearAllMocks` и делает тест зелёным по чужому остатку (04.10.2026, этап 34, N2)** — `social.test.js` добавил `pool.query.mockReset()` в общий `beforeEach`, и тест `POST /api/likes` сразу стал красным с 500. Оказалось, у него **не хватало одного значения** в очереди моков (роут делает 7 запросов, было заведено 6), и шестое-седьмое он годами добирал остатком очереди из предыдущего теста. В полном прогоне это всегда работает, в одиночном — нет, то есть зелёный результат держался на порядке объявления тестов. Лечение: `mockReset()` в `beforeEach` плюс **полная очередь в каждом тесте** — тест, который падает от честного сброса моков, был зелёным не по своей причине. Общее правило: **`clearAllMocks` чистит вызовы, но не очередь `...Once`**; тест, зелёный только в полном прогоне, проверяет не то, что кажется.

77. **`git checkout -- <файл>` откатывает не только ломку, но и незакоммиченную работу (04.10.2026, этап 34, N2)** — ломка гейта проверяется так: внести правку, прогнать, вернуть файл. Возврат через `git checkout --` уничтожает **всё**, что в файле не закоммичено, — включая основную правку этапа, если она ещё не в коммите (в этом эпизоде так и вышло: курсорная пагинация фронта была стёрта вместе с ломкой, пришлось восстанавливать шесть правок по памяти и заново прогонять тесты). Правильно: **снимок байтов в temp перед ломкой и запись байтов обратно** (скрипт делает это сам и печатает `идентичен`/`ОТЛИЧАЕТСЯ` в конце — сверка обязательна, иначе «откатил» и «забыл» неразличимы). Общее правило: **откат в эксперименте должен быть точной копией снимка**, а не командой, которая молча опирается на состояние индекса git.

78. **Гейт, сверяющий реальность с собственной константой, зелёный на настоящей дыре (04.10.2026, этап 35, N8)** — `scripts/secrets-leak-audit.mjs` проверял rsync-строку `deploy.yml` списком `['.env', '*.secret', '*.pem', '*.key', 'uploads']`: список лежит в коде гейта, и гейт проверяет, что эти пять строк есть. Всё, чего в списке нет, не проверяется вообще — поэтому `server/.jwt-dev-secret` (`.gitignore:32`), `.env.local`, `*.pfx`, `id_rsa` **ехали на VPS**, а гейт был зелёный три года. Дыра тут не в rsync, а в проверке: гейт знает, какие файлы считает секретами (`SECRET_FILE_RE`, 6 классов), и обязан сверять с этим знанием, а не с собственным перечислением. Лечение: список образцов имён (по одному на каждую ветку регулярки) и **вычисляемое покрытие** — «каждый образец обязан матчиться хотя бы одним `--exclude`». Общее правило: **обязательный список в проверке и список сущностей в проверяемой системе — одно и то же знание, а не два независимых**; дублирование даёт гейт, который не может упасть.

79. **Проверка «какие файлы лежат на диске» в CI зелёна по построению (04.10.2026, этап 35, N8)** — естественный способ закрыть N8 — обойти дерево и потребовать, чтобы каждый найденный файл-секрет был исключён из rsync. Это не работает: после `actions/checkout` незакоммиченных файлов в рабочем дереве **нет вообще** (`.env`, `.jwt-dev-secret` — в `.gitignore`), гейт нашёл бы ноль файлов и радостно стал зелёным на том же дефекте. Канал проверки обязан опираться на **классы имён**, известные и в CI: список образцов сверяется с шаблонами rsync, а не с файловой системой. Общее правило: **проверка, чей предмет проверки не попадает в CI, зеленеет по построению** — сначала спроси, существует ли этот предмет на машине, где гейт запускается.

80. **Семантика шаблонов rsync и docker противоположна; матчер с чужой семантикой зеленит сломанный workflow (04.10.2026, этап 35, N8)** — в `.dockerignore` `.env` исключает **только корневой** файл, а `**/.env` — все; в rsync наоборот, шаблон **без слеша матчит basename на любой глубине**, поэтому `.env` закрывает и `server/.env`, и не требует `**/`. Гейт написал мини-матчер с docker-семантикой (он уже был в гейте для `.dockerignore`) — и такой матчер объявляет `*.secret` покрытием `.jwt-dev-secret`, то есть **исправляет гейт, не чиня workflow**. Доказано прогоном B3: с matcher'ом по docker-семантике сам гейт **exit 0**, красны только тесты гейта. Общее правило: **семантика проверяемого формата выносится в отдельную функцию и фиксируется тестами на обеих противоположных парах** (`config/*.pem` не матчит `server/config/tls.pem`, `*.key` матчит `nested/dir/tls.key`); общий код для двух форматов — это не переиспользование, а способ сделать одну из проверок декоративной.

81. **`^` в регулярке без флага `m` привязан к началу всего блока, а не каждой строки — проверка «есть ли в блоке строка» молча всегда ложна (05.10.2026, этап 36, N1)** — проверка `npm test || true` была записана как `/^\s*(?:- )?run:.*\|\|\s*true/.test(code)`, где `code` — многострочный блок джобы из `ci.yml`. Без флага `m` `^` совпадает только с позицией 0, а блок начинается с `  test-server:` — проверка **никогда не срабатывала**, то есть джоба с `|| true` проходила гейт. Нашлось это не чтением кода, а падением теста: скрипт ломки искал подстроку и находил, гейт — нет. Общее правило: **регулярка с якорем `^`/`$`, применённая к блоку, обязана нести `m`; надёжнее — не полагаться на якорь вовсе** (`/continue-on-error:\s*true/` без якорей работает на любой строке), а тест гейта обязан содержать случай, где искомая строка стоит **внутри** блока, а не в начале.

82. **Ломка, бьющая по первому совпадению, а не по своей цели, остаётся зелёной и доказывает ноль (05.10.2026, этап 36, N1)** — ломка B1 вырезала блок `services:` из `ci.yml`, чтобы джоба `test-server` осталась без БД. Поиск шёл по `/^ {4}services:$/` по всему файлу и нашёл **джобу `e2e`** (она тоже объявляет сервис mysql) — изломался не тот объект, гейт остался зелёным, и «доказанная» ломка на самом деле ничего не доказала. Это второй случай одной грабли (питфолл 66) в новой обёрстке, и спасение только одно: **границы сущности вычисляются явно** (сначала найти блок джобы, потом искать внутри него). Общее правило: **пока не проверено «а тот ли это объект», ломка недействительна**, а зелёный результат ломки при исправном гейте — это не «гейт слишком строгий», а «ломали не то».

83. **`afterAll` выполняется даже после падения `beforeAll` — защита только в `beforeAll` прячет внятную ошибку под невнятную (05.10.2026, этап 36, N1)** — в `race.mysql.test.js` `beforeAll` получил явную проверку `if (!admin) throw new Error('MySQL недоступен по host:port')`, а `afterAll` остался прежним: `await admin.query(...)`. При недоступной БД вывод содержал **две** ошибки, и второй была `TypeError: Cannot read properties of null (reading 'query')` — первая, полезная, терялась в шуме, и читатель вывода не понимал, что произошло. Общее правило: **`skipIf` и проверки в `beforeAll` не отменяют `afterAll`**; каждая функция очистки обязана сама переживать то состояние, ради которого её писали, иначе диагностика теряется ровно в том прогоне, который её вызвал.

84. **Один и тот же «пропуск» честен локально и замаскирован в CI, если режим не объявлен флагом (05.10.2026, этап 36, N1)** — `describe.skipIf(!admin)` на машине без MySQL это удобство, а в джобе без сервиса БД — замаскированный ноль выполненных проверок: год зелёных джоб при полном пропуске единственного теста на настоящем движке. Попытка «просто убрать skipIf» ломает разработчика без локальной БД (`npm test` начинает падать), и такой гейт быстро отключают. Правильное решение — **режим по флагу окружения**: `REQUIRE_MYSQL=1` превращает пропуск в падение, локально флага нет и `npm test` зелёный. Общее правило: **тест, который умеет пропускаться, обязан иметь явный способ требовать себя**, а гейт обязан проверять, что этот способ включён именно там, где пропуск недопустим.

85. **Ломка, которая правит не то, чем задумано, всё равно «доказывает» гейт (05.10.2026, этап 37, N4)** — доказательство ломки B1 («код-валидатор шире CHECK») строилось так: строка файла бралась регуляркой, экранировалась через `replace(/[.*+?^${}()|[\]\\]/g, '\\$&')` — и **экранированная строка подставлялась обратно как замена**. В файл попали обратные слэши (`intField\(rawHeight...`), `findCodeRangeValidators` перестал видеть валидатор (в фактах было «код-валидаторов intField: 3» вместо 4), и гейт покраснел — но **по другой находке** («CHECK не проверяется кодом» вместо «валидатор разрешает 0..250»). Формально ломка сработала, по факту она доказала совсем другой класс дефектов, а настоящая проверка П1 осталась недоказанной. Общее правило: **доказательство ломки обязано утверждать не только «гейт красный», но и «красный по ожидаемой причине»** — сверять конкретный текст находки; иначе зелёный отчёт о ломках доказывает только то, что гейт где-то падает.

86. **Механическое отбрасывание окончания ломает английские слова (05.10.2026, этап 37, N4)** — `singular()` для связывания имён делал `word.endsWith('s') && !word.endsWith('ss') ? word.slice(0, -1) : word`, и `singular('status')` давал `'statu'`. Связь `HANGOUT_STATUSES` ↔ `hangouts.status` при этом ещё вытягивалась запасным правилом, но `wordsOf` засорнялся мусорными словами, а любое слово на `-us`/`-is` (`plus`, `analysis`) давало несуществующее. Общее правило: **морфология в гейтах — это словарь исключений, а не регулярка**: окончания `-us`/`-is` не трогаются, а сама функция обязана иметь тест на слова-ловушки (`status` → `status`, `categories` → `category`), иначе первый прогон на реальных данных падает в неочевидном месте.

87. **«Файл обращается к таблице» ≠ «список относится к этой таблице» — признак принадлежности, взятый из файла, даёт ложный класс находок (05.10.2026, этап 37, N4)** — первая версия гейта связывала именованный список кода с ENUM-колонкой так: «файл, где объявлен список, упоминает таблицу с такой колонкой». `hangouts.js` упоминает `partner_offers`, поэтому `HANGOUT_CATEGORIES` (категории встречи) проверялся против `partner_offers.category` (категории оффера) и давал находку «theater|exhibition|cafe|concert|sport|other», которой в проекте нет. Общее правило: **принадлежность объекта к сущности выводится из имени сущности или из близости операции записи, а не из факта, что они оказались в одном файле**; связь строится по словам имени (`validTags` ↔ `tag`, `type` ↔ `conversion_type`) и по расстоянию до `INSERT`/`UPDATE` в пределах фиксированного окна, а объединение значений нескольких кандидатов фиксируется как осознанное ослабление в тексте гейта.

88. **Проверка «объявлено, но не используется» без учёта экспорта объявляет живой список мёртвым (05.10.2026, этап 37, N4)** — счёт использований велся по файлу объявления, и `CHANNELS` из `notification-prefs.js` (экспортируется и читается в `routes/notifications.js` трижды) получал находку «список объявлен, но нигде не используется». Общее правило: **«используется» — это свойство репозитория, а не файла**: экспорт и импорт считаются применением, иначе гейт наказывает за модульность, а не за дыру.

89. **Покрытие ограничения, найденное по всем упоминаниям сущности, требует валидатор и там, где сущность только читается (05.10.2026, этап 37, N4)** — проверка «диапазонный CHECK покрыт кодом» искала писателей по `FROM`/`JOIN` вместе с `INSERT`/`UPDATE`, и на фикстуре падала с требованием валидатора в файле, который читает `user_profiles` ради ленты: ограничение защищает **запись**, читатель клиентский ввод не передаёт. Общее правило: **ограничение и проверка связаны через операцию записи**; «кто касается сущности» — слишком широкое условие для гейта, который должен требовать проверку только там, где она влияет на данные.
